# Changelog

All notable changes to the PACT plugin, newest first. Each version's section
is that version's GitHub release: when a version bump reaches `main`,
`.github/workflows/release.yml` tags it and publishes the section.

Format: a section starts with `## v<version>: <short summary>`, where the
summary is printable ASCII, em dash or en dash only and the text after `## `
becomes the tag message, followed by `### Summary`, `### What landed` and
`### Why`. A section ends at the next `## vX.Y.Z: ` heading. To keep the
section split identical to what GitHub renders, the file uses a restricted
Markdown: LF line endings; no HTML comments or HTML blocks; no fenced code
blocks (no run of three backticks or three tildes anywhere; inline `code` is
fine); no collapsible details or summary HTML tags; no line starting with
`<` (write links as `[text](url)`); no lines made only of `=` or `-`; and
every heading that names a version is exactly `## vX.Y.Z: <short summary>` at
column 0. Inside a section use `###` or deeper; an `## [Unreleased]` heading
goes only above the newest version. Every PR checks the whole file with
`.github/scripts/check-release-notes.sh`.

## v4.8.32: capture comparable full-suite diagnostic outcomes

### Summary

The full-suite workflow's manual dispatch can now select whole-file or per-test xdist scheduling while keeping whole-file scheduling as the default everywhere else. Manual runs also emit JUnit XML and upload it with the existing collection and run records, so diagnostic comparisons can detect per-test outcome changes without replacing the schema-v3 merge-gate evidence.

### What landed

- `.github/workflows/tests.yml` adds a constrained `dist` dispatch choice: `loadfile` by default, with `load` as the only alternative. The single unrestricted pytest invocation has no path operands and resolves to the existing default command outside explicit diagnostic dispatches. The required `full-suite` job remains scalar, and the existing full-collection, full-run, and before/after environment verifiers keep their ordering.
- The pytest step writes `.full-suite-results.xml`. A dispatch-only, always-run upload step preserves that JUnit file, `.full-run-record.json`, and `.full-collection-record.json` under a unique run/attempt artifact name. Missing evidence is an error, and `include-hidden-files: true` is mandatory for these dotfiles. The upload action is pinned to `actions/upload-artifact` v7.0.2 by full commit SHA; merge-group and push runs gain no artifact dependency.
- CI contract tests pin the input, exact dynamic command, artifact shape and placement, action allowlist and pin, and final environment check. One strict `shlex` normalizer accepts only the reviewed dynamic command and resolves it to the static default for local collection parity; expression fragments, extra arguments, missing JUnit output, and selection flags fail instead of reaching local pytest. Mutation arms cover altered commands, hidden-file omission, missing paths, wrong upload conditions or placement, and unpinned actions.
- `scripts/compare_full_suite_results.py` and its focused tests compare per-test JUnit outcomes without replacing schema-v3 certification. The comparator preserves duplicate cases, reconciles raw XPASS evidence and skip identities, and fails closed on missing or ambiguous evidence; it also normalizes the real Actions log envelope, quoted distribution arguments, summary timing skew, and invocation-relative skip paths.
- `pact-plugin/tests/test_memory_store_isolation.py` removes the predecessor sentinel that made memory-init reset verification depend on test order and worker placement. Both tests now establish their own initialized state, and the reset test calls the owner reset before its unchanged clean-state assertion; standalone, reversed-order, xdist-load, and reset-removal controls cover the isolation.
- `pact-plugin/tests/test_merge_guard_perf.py` pairs target and reference timing observations so normalized cost no longer depends on separately timed blocks, and uses median raw target times to reject size-specific fast outliers without hiding sustained quadratic scaling. Best-of-K normalized cost, the 3.0 raw ratio bound, the 4000.0 ceiling, and unbounded-prefix detection remain, with fake-clock and mutation controls proving the schedules still detect regressions.
- `scripts/verify-gate-tree.sh` now brackets local pytest with before/after HEAD and complete porcelain comparisons. Stable, moved, and red-child runs are distinguished explicitly, green moved trees become unattributable, and capture paths inside the declared tree are refused before any snapshot or test work. The canary requires the new evidence while decisive certification still uses a detached clean worktree.
- Instruction-surface tests for corpus writers, markers, lazy-load cross-references, and peer injection now enumerate their intended tracked files rather than stray untracked matches. Local controls check root/pattern filtering, known members, deletion detection, empty-population refusal, and the original raw-glob failure mode.
- Harvest, import-bar, non-TTY, manifest, prose-root, and Python-floor tests now enumerate their shipped populations from git while retaining synthetic and intentional disk-based discovery. Known-member, untracked-exclusion, deletion, and count controls prove the new oracles are non-vacuous. The import-bar synthetic model also copies only its two tracked Python sources, closing the fixture-copy path around tracked enumeration without weakening deletion checks.
- Post-merge, session-context, store-access, run-scope, and wake-ordering tests now use checked Git-index pathspecs for shipped artifacts while preserving deleted-member failures and synthetic temporary-root walks. Twenty-three before/after probes and three real deletion controls verify the isolation.
- Agent, command, and skill structure tests now enumerate shipped files from the Git index with nonempty, rooted, and known-member controls. Filesystem walking remains only for gitless exports, while deleted tracked entries stay visible and raw-walk mutation controls preserve the original failure signal.
- Verification closed 45 of 45 confirmed run-dependent walk hits across 18 modules, with untracked-match probes inert and required tracked-deletion controls preserved. The 28-module focused set reported 3,000 passed and 1 skipped under both `loadfile` and `load`; the final 10+4 fixed-head CI matrix produced 14 valid runs, each with 31,581 passed, 28 skipped, 0 failed, and 0 errors, with zero per-test outcome deltas and no evidence errors.

### Why

Repeated diagnostic runs need per-test evidence, not only aggregate counts: equal totals can hide two tests swapping pass and skip. JUnit adds that comparison surface beside the existing certification records, while the constrained dispatch interface exposes per-test scheduling without arbitrary pytest arguments or a new job matrix. The tracked-population, memory, timing, and tree-attribution fixes remove local run conditions that could change test outcomes or make a green run unattributable, so repeated runs measure the same shipped suite.

## v4.8.30: hold the cold report until its round's warm reviewers are accepted or stopped

### Summary

The peer-review cold lane's report is now held in the lead's context, and written to no file, while any warm reviewer of the report's round still holds the release, instead of being appended to the record the moment it returns. A warm reviewer stops holding the release in one of two ways: the lead accepts a HANDOFF it delivered for that round, or it is stopped with `TaskStop`. The hold also covers the lead's other files that carry a finding or a disposition, its `review_finding` journal writes, and the messages and task text a holding reviewer can read. The trade-off is durability: a held report exists only in the lead's context, so a context compaction can lose it; **Return** names the degraded path instead of promising a recovery.

### What landed

- `commands/peer-review.md` **Return**, who holds the release and how it ends: a warm reviewer of the report's round is one the lead dispatched in that round or reused in it by `SendMessage`, as in a verify-only re-review round. It holds the release until the lead accepts a HANDOFF it delivered for that round, or until it is stopped with `TaskStop`; a `TaskStop` that reports the agent not found counts as stopped. A replacement that `/PACT:imPACT` calls for holds the release from that moment, before the lead stops its predecessor or spawns it. The lead accepts a HANDOFF by validating it, marking its task `completed` and sending the acceptance `SendMessage`, the acceptance pair in Completion Authority; a reviewer's task status is not a delivery, and a task marked `completed` by termination, stall recovery or a redo is not an acceptance.
- **Return**, what keeps holding the release: every other `/PACT:imPACT` outcome (continue, augment, escalate, redo, `/PACT:rePACT`, re-invoke), and stall recovery that marks the task `completed` and spawns a new teammate without `TaskStop`: the old teammate holds the release until the lead stops it with `TaskStop`, which the lead does once the new teammate is spawned, and the new teammate holds it too. A delivered HANDOFF awaiting the lead's decision is not a stop and keeps holding the release. A warm reviewer that is making no progress counts as a stop when it has delivered no HANDOFF, or when the lead rejected its HANDOFF and it has drawn no revised HANDOFF; the lead runs `/PACT:imPACT` on it, and the stop itself releases nothing. A reviewer that becomes live again in the round, because its HANDOFF was rejected and is under revision, it was re-dispatched by `/PACT:imPACT`, it was sent new work by `SendMessage`, or it was resumed after a `TaskStop` by any `SendMessage` to its name, holds the release again until the lead accepts its new HANDOFF or it is stopped with `TaskStop`.
- **Return**, what the hold covers: the review doc, a sibling file and a scratch file are named as the same leak. The hold covers every other file of the lead's that would carry a finding or a disposition, the synthesis included, and every `review_finding` journal write. It also keeps a held cold finding out of a `SendMessage` to a holding reviewer or to the secretary, out of the subject, description or metadata of a task assigned to a holding reviewer or named in its task, and out of the subject, description or metadata of any task the lead creates. The hold delays writes and messages only; it does not delay triage. The one write it does not cover is the spawn-time agentId and placeholder record.
- **Return**, the release and a lost report: the held report and held files are written when no warm reviewer of the report's round still holds the release, in every case before the synthesis is written. A held report that can no longer be reproduced verbatim routes by type: a report other than a same-round re-check is treated as no report under the existing one-fresh-dispatch bound, ending with the "Cold lane did not run" row and line when that bound is spent, while a lost same-round re-check report falls back to the valid first-round report as the round's end state, with no fresh dispatch.
- **Return**, the placeholder-correction line: the lead line recording placeholder values corrected by `/PACT:imPACT` is appended immediately after the report it corrects. When that report is already in the record, the line is appended as soon as `/PACT:imPACT` returns; while the report is held, the line is held with it and appended immediately after it at the release.
- `commands/peer-review.md` **Synthesis**: while a warm reviewer of the round still holds the release, the synthesis is held in the lead's context too, and no file that carries a finding or a disposition is written until the release **Return** gives.

### Why

The cold lane is dispatched in the same parallel block as the warm lanes, but its report reached live warm reviewers when the lead wrote it to the record: a file this session writes reaches a live teammate's context when it changes, whatever its location. A warm reviewer that has read the cold report turns an overlap between the lanes into a reproduction rather than an independent find. Holding the report, and keeping held findings out of what a holding reviewer reads, keeps the warm lanes' findings independent of the cold read while they are still being produced. It does not make the warm lanes independent of each other. The durability trade-off is real: the hold exists only in the lead's context, and the degraded path names what to do when that context no longer carries the text.

## v4.8.28: certify the full-suite run record under pytest-xdist

### Summary

The merge-gate run record can now be certified when the suite runs under `pytest-xdist`. Each worker publishes its own collection counts, and the controller records them only when every worker that started reported the same counts and they match the session's collected total. When no faithful value exists, the count fields stay null and the verifier fails closed. The full-run verifier also refuses a run whose pytest exit status is not 0, and an allowlist entry that no skip used.

### What landed

- `tests/ci_full_run_record.py`: an xdist worker publishes its `(before, after, deselected)` triple through `workeroutput` and writes no record. The controller keys each published triple and each ready node by the node's gateway id, so a repeated down event cannot stand in for a missing worker. It writes the triple only when every ready node reported one, all agree, and `after` equals the session's collected count; otherwise both item fields and `deselected` are null and a diagnostic names the reason. Deselection comes from each worker's `pytest_deselected`, which keeps silent hook narrowing distinguishable from a reported deselection. Distribution is detected the way xdist detects it (`--tx` set and `--dist` not `no`), so a `--tx` run without `-n` is recorded too. Both node hooks share the same ownership guard, the ready-node population is a required argument, and the controller hook is an optional hook so sessions that run with `-p no:xdist` still load the plugin. A serial run's record is unchanged.
- `scripts/verify_full_run.py`: a record whose `exitstatus` is not 0 fails with `EXITSTATUS`. An allowlist entry that matches no recorded skip site fails with `SKIP-ALLOWLIST-UNUSED`; this check runs in the full-run verifier only, not in the fast-lane summary. An empty allowlist is now valid, so a run with no skips can still certify.
- `scripts/full_suite_skip_allowlist.json`: one entry admits the three xdist integration tests while xdist is not in the CI constraints; its description says an entry is removed in the commit that stops its skip.
- `tests/test_ci_full_run_record.py` and `tests/test_verify_full_run.py`: pure-function tests cover every refusal branch of the aggregate, and seam-free tests drive the worker publish branch and the controller success path without xdist installed, so the wiring is guarded in CI. Three integration tests run the real xdist path when it is installed and skip otherwise; one drives a worker internal error raised after that worker's tests, where the session exits 0 and the ready-node comparison is the only refusal.

### Why

Under `pytest-xdist` the controller never collects, so every distributed run failed certification on a null collection count and xdist could not be adopted. The counts are not additive: every worker collects the whole suite, so a sum would be several times the corpus. The only faithful aggregate is the value every worker reports identically, and anything short of that must leave the record unprovable rather than plausible.

## v4.8.27: the orchestrator relays milestones instead of falling silent

### Summary

The orchestrator's wait-in-silence rule now separates narration from a milestone. It stays silent on "waiting on X" and "still running". It reports a milestone, meaning something the user would act on and cannot otherwise see: a dispatch's result, a measured number, or a state change. The report is one line that carries the concrete fact rather than a description of the activity. The orchestrator relays each milestone as it reaches it, without being asked, and never polls or nudges a teammate to get one. When it wants a long dispatch reported mid-run, it asks for progress signals in that dispatch's brief, so the user sees milestones as they land rather than asking for status.

### What landed

- `agents/pact-orchestrator.md` §Wait in Silence: the list that defines a turn with no actionable content now includes "no milestone the user is owed", so that sentence is complete on its own.
- The same section gains one paragraph, placed immediately after that rule. It does the following:
  - It defines a milestone as something the user would act on and cannot otherwise see. That qualifier governs all three kinds: a dispatch's result, a measured number, and a state change.
  - It requires the relay to be one line addressed to the user. The line carries the concrete fact, and is sent only when the fact is new since the last report to the user and is not a running tally of the same work.
  - It states the tally test for a fan-out: a count of members finished is a tally, and a member's result the user would act on is a milestone.
  - It states that "No actionable content" means nothing the team needs AND nothing the user is owed.
  - It makes the orchestrator relay each milestone as it reaches it, never poll or nudge a teammate to obtain one, and ask for progress signals in the brief of a dispatch it wants reported mid-run.
  - It bounds that ban: a nudge that resolves an ambiguous teammate state under §12 Intentional Waiting is not polling for a milestone, and a milestone carried by its reply is relayed like any other.
- The paragraph separates narration from a milestone rather than carving an exception out of the silence rule. Filler calls stay with the filler-call rule, not the narration list. The surrounding anti-narration, filler-call and watcher rules keep their full force: none of their pinned phrases changed, and the section was not restructured.

### Why

The silence rule named only what is actionable for the team, so its safe reading was silence on everything. Between dispatch and the awaited event the only interim progress signal arrived in teammate notifications the user never sees. The watcher rules already require the completion report; nothing required an interim one, so the user had to ask for status repeatedly. Naming the milestone case changes what the orchestrator does on a teammate turn, without reopening the narrate-the-wait and filler-call failures the section exists to prevent.

## v4.8.25: verify-only re-review reports carry two required lines

### Summary

Every warm verify-only re-review report now carries two required lines: **Reader false flags**, naming each check's relevant input scope and outcome and each result it got wrong, and **Declined items**, naming each checklist item the reviewer did not satisfy together with the measured evidence that the artifact is correct. Checks that error, have empty input or an empty test selection, cannot read their target, or target the wrong input make verification incomplete: they cannot use the clean empty form or support `resolved`. For a completed, correctly scoped check with no false flags, the empty case is an explicit token rather than an omission, so an omitted line is unauditable and is sent back instead of being read as a clean pass. The contract has a single home in the verify-only section of the peer-review command, and the Format row names it. The cold lane keeps its existing finding-status `RE-REVIEW CHECKLIST` and coverage-boundary receipt; only the two new report lines are warm-only.

### What landed

- `commands/peer-review.md` carries the contract immediately below the verify-only comparison table. Both lines are mandatory; line one carries each check's relevant input scope and outcome, and its clean empty form names that scope and outcome, so "none" is a claim about a completed, correctly scoped check rather than silence. Checks that error, have empty input or an empty test selection, cannot read their target, or target the wrong input make verification incomplete and cannot support `resolved`.
- The Format row in the same table is extended to read `Checklist: finding → resolved / not resolved / new issue, plus the two warm report lines below`, so a lead reading only the table still sees that the report owes more than the checklist and cannot apply it to the cold lane.
- The block names both dispatch routes: the description of the warm reviewer task the round creates for the review work, and the `SendMessage` when the warm reviewer is reused. Both carry the full line definitions, never a pointer, because a warm reviewer never loads the command file.
- Neither line is a finding: neither is journaled as a `review_finding` and neither is counted in a finding class, so a diligent report cannot fail the cycle it is verifying by re-raising a closed class.
- The cold lane keeps its existing finding-status `RE-REVIEW CHECKLIST` and coverage-boundary receipt; only the two new report lines are warm-only, so the exclusion cannot be read as weakening either cold obligation.
- A new presence pin guards the contract: the block exactly once inside its section and once in the file, the amended Format row, the two labels absent from a cold-lane section proven live by a known-present token, and the relay and journal-exclusion tokens. Its liveness control reads the command file, re-wraps the verify-only region, splices it back, and proves the block arm still matches, so a harmless reflow cannot redden the pin and a raw comparison would; the module docstring states the ceiling, that a presence pin certifies text and never behaviour.

### Why

A verify-only report said "all resolved" whether the check had run correctly or could not see, and it said nothing about checklist items a reviewer declined to satisfy. The first case hides a broken check behind a green verdict; the second invites editing a correct artifact to make an over-specified checklist green. Naming both, and binding the first to a completed, correctly scoped check, makes the report auditable against the artifact, and keeping them out of the finding journal keeps them report-level evidence rather than reopened findings.

# Changelog

All notable changes to the PACT plugin, newest first. Each version's section
is that version's GitHub release: when a version bump reaches `main`,
`.github/workflows/release.yml` tags it and publishes the section.

Format: a section starts with `## v<version>: <short summary>`, where the
summary is printable ASCII, em dash or en dash only and the text after `## `
becomes the tag message, followed by `### Summary`, `### What landed` and
`### Why`. A section ends at the next `## vX.Y.Z: ` heading. To keep the
section split identical to what GitHub renders, the file uses a restricted
Markdown: LF line endings; no HTML comments or HTML blocks; no fenced code
blocks (no run of three backticks or three tildes anywhere; inline `code` is
fine); no collapsible details or summary HTML tags; no line starting with
`<` (write links as `[text](url)`); no lines made only of `=` or `-`; and
every heading that names a version is exactly `## vX.Y.Z: <short summary>` at
column 0. Inside a section use `###` or deeper; an `## [Unreleased]` heading
goes only above the newest version. Every PR checks the whole file with
`.github/scripts/check-release-notes.sh`.

## v4.8.39: key project memory by repository identity, not folder name

### Summary

pact-memory now files a project's memories under the repository they belong to, not under the folder the repository was cloned into. A checkout whose `origin` is `git@github.com:Acme/Widget.git` uses the id `github.com/acme/widget` on every machine and in every folder, so copying `memory.db` to another machine no longer loses a project's memories, and two unrelated repositories cloned into folders with the same name no longer share one bucket. A project with no remote, or whose origin is a remote-helper transport such as `codecommit::`, keeps its folder-name bucket and still shares it with any folder of that name, as before. Memories saved under the old folder name are read only while there is evidence they belong to this repository: a file row under it, or a session started at its root that is still on disk or in the new session ledger. In a long-lived store most pre-upgrade buckets will have neither, because their file rows are usually relative and their sessions are older than the 30-day session cleanup, which wrote no ledger line before this release. Those buckets are reported as `unproven` and are not read until the user approves a `project-id rekey`, which moves them to the new id for good. When pact-memory cannot tell which repository a checkout is, it refuses and names the fix instead of quietly falling back to the folder name.

### What changes for you

- **The id.** It is `host/owner/repo` from the repository's `origin` remote. ssh, scp and https spellings of one remote give one id; the host is lower-cased; the login (except in a `~` home path), a trailing `.git` and a scheme's default port are dropped, and any other port is kept. A folder with no remote, or a local-path remote, keeps its folder name as before.
- **An explicit pin.** A user can write a canonical id to `<git-common-dir>/pact-project-id`, shared by every worktree of the repository. It outranks the remote. An in-tree `.pact/project-id` is ignored, because a clone can plant one, and a folder-name value is ignored and reported as `override_ignored`.
- **A project with no remote shares its bucket, as before.** A project whose id is its folder name (a repository with no portable origin, a non-git project folder, the home-directory landing, or the user-scope `project_id` setting) reads and saves its same-name bucket exactly as before this change, so it shares that bucket with every folder of the same name. To give it its own id, add an `origin` remote or write a canonical id to `<git-common-dir>/pact-project-id`.
- **Old memories.** Reads also cover this checkout's old folder-name bucket while it holds rows, when a file row places it in this repository or a session started at this repository's root wrote into it, and nothing places it elsewhere. One ownership rule decides this for every reader, the save guard and the defaulted rekey: a bucket is kept out only on positive evidence of another owner, so rows that are gone, unreadable or outside any other checkout no longer exclude it. A bucket with no evidence either way is reported as `unproven` and is not read; `list`, `search` and `project-id show` name it with the command that moves it. Every new save goes to the new id.
- **New commands.** `project-id show` reports the id, how it was chosen, what reads cover, every populated bucket and a runnable rekey command where one is safe. `project-id rekey --from=<id> --to=<id>` moves a whole bucket (memories, file rows, links and vectors) in one transaction. It is a dry run unless you pass `--apply`, and a second apply changes nothing.
- **Refusals instead of guesses.** A remote that cannot be represented, a `.git` git cannot answer for, a `.git` that points into another repository, or a submodule with no usable remote refuses with the cause and the fix. `project-id show` and `status` carry it as `decline_reason`.
- **Exit codes.** Every command now exits 3 for an operational fault: a store that cannot be opened, read or written, a failed `setup`, a `save` whose read-back found no row, or an unexpected internal error. These exited 2 before; exit 2 now means bad input only.
- **Reads no longer change an existing store's schema.** `list`, `search`, `sync`, `status`, `get` and `project-id show` no longer create the schema of, migrate or change the journal mode of an existing store; a read can still add vector rows for memories not yet embedded. The first `list`, `search`, `status` or `get` of an absent store in the default location creates it with its schema and answers empty; `project-id show` creates nothing.
- **A rekey of this checkout's old bucket says how many memories came from no recorded session.** `project-id rekey --from` this checkout's legacy folder-name bucket (the dry run and `--apply`) states, once per run, the count of its memories that no recorded session wrote, which the move carries with the bucket. A rekey of any other bucket prints no such count.
- **Mixed versions.** An older plugin version sharing the same store (another machine, or a downgrade) still reads only folder-name buckets, so it does not see rows saved under a repository id or moved there by `project-id rekey`.
- **A stale Working Memory section is emptied.** `sync` for a resolved id with no memories rewrites a Working Memory section whose every entry names, by its Memory ID, a row of a bucket this read hides for this checkout (the old folder-name bucket when unproven or excluded, a case variant or ambiguous match of it, or a submodule's suppressed name) with the current comment and no entry, and reports `wrote`. Any other section (no entry, or an entry naming another row, as in a committed CLAUDE.md on a new clone), a fresh store and a declined identity are left as they are.
- **The backlog file name** stays keyed by the folder name, because it is a path and a canonical id contains slashes.

### Identity details

- github.com owner and repository names are lower-cased, in a remote or a pin, on any port, because GitHub treats them case-insensitively, and github.com drops only a lower-case `.git` suffix, as every other host does (`https://github.com/O/R.GIT` gives `github.com/o/r.git`, and the backlog reads it as `o`/`r.git`); every other host, GitHub Enterprise and a ported `www.github.com` included, keeps the path's case, so two case spellings there are two ids until rekeyed.
- Percent-encoded and non-ASCII path characters are kept as uppercase `%XX` on every host except a port-less github.com (see its name rule below), except that an escaped unreserved character (a letter, digit, `-`, `.`, `_` or `~`, such as `%41`) is decoded, and the Azure DevOps https, ssh and `visualstudio.com` spellings of one repository share one id. `ssh+git://` is accepted. An ssh host alias stays in the id, because git cannot tell an alias from a host. An ssh or scp alias may hold an underscore (`git@gh_work:o/r.git` gives `gh_work/o/r`), as a hyphenated one may; other transports still decline an underscore host. An alias id matches only clones whose origin uses the same alias, usually those on machines whose ssh config defines it; a pin holding the canonical id (`github.com/o/r`) joins an alias clone to the others. A git `insteadOf` alias is kept as written too: `gh:acme/widget` gives `gh/acme/widget`, and the same pin joins it.
- A remote whose host is `invalid` or ends in `.invalid` (RFC 2606) now declines (`origin_unrepresentable`) instead of deriving an id.
- A remote with a bracketed IPv6 host (`ssh://git@[2001:db8::1]/o/r.git`, `https://[2001:db8::1]:8443/o/r`, `git@[2001:db8::1]:o/r`) now gives a canonical id, the address in its one compressed spelling inside brackets, instead of declining. A zone index (`%eth0`) still declines, and so does an IPv4-mapped literal (`[::ffff:192.0.2.1]`), since the same server has a plain IPv4 spelling; a pin holding one is not canonical.
- A `GIT_DISCOVERY_ACROSS_FILESYSTEM` value git cannot parse is now read the same way, as true (fail closed), by both the identity resolver and the CLAUDE.md project-root walk; before, one read it as false.
- A remote with an empty port (`ssh://git@host:/o/r`, `https://host:/o/r`) is the same server as one with no port, as git treats it, and gets the same id; it used to decline.
- A remote host with an empty label (`a..b`) now declines, and an id holding one is not canonical; it used to give the id `a..b/o/r`.
- An ssh or scp remote on GitHub's SSH-over-443 host (`ssh://git@ssh.github.com:443/O/R`, or `ssh.github.com` with no port) gets github.com's id; another port on that host, and an https remote naming `ssh.github.com`, keep their own id.
- `https://www.github.com/O/R` gets github.com's id, as GitHub redirects `www` to github.com.
- The backlog reads its github.com repository from the memory id itself, so the two always agree on a remote: every spelling the id accepts gives the same owner/repo (lower-cased), and every spelling it declines (a query or fragment tail, a leading-zero port) gives none. It reads the first `remote.origin.url` of the repository's own config, as the memory id does. It finds the repository's git directory with the same reader the id uses, so it works on every git version the id supports.
- A pin is read with GitHub's spelling rules, as a remote is. Its host is case-insensitive (`GitHub.com/Acme/Widget` names `github.com/acme/widget`, and `H.Example/o/r` names `h.example/o/r`), and a port-less `github.com` or `www.github.com` pin has each name decoded and lower-cased, as its remote does (`www` becomes `github.com`, `%41b` becomes `ab`), so `github.com/Acme/Widget` names `github.com/acme/widget`, and a port-less `github.com` pin is refused as not canonical when it is not exactly owner/repo or its owner or repo holds a character a GitHub name cannot (see the name rule below), as such a remote declines. A ported `github.com` pin is lower-cased outside its `%XX` escapes, as its remote is. A pin's escaped path characters are read as a remote's are: an escaped unreserved character is decoded in either hex case (`%41` and `%6a` give `A` and `j`, `%2d` gives `-`), so a pin and the remote naming the same path give one id on any host and port; any other escape in a pin must be upper-case hex (a lower-case `%c3` or `%2f` is refused as not canonical, while `%C3` and `%2F` are kept). A ported `www.github.com` and other hosts keep their path's case.
- A port-less github.com pin whose repository ends in `.git` (`github.com/acme/widget.git`) is honoured as written. It is the id a remote spelled `widget.GIT` or `widget.git.git` gives, not the id of a remote spelled `widget` or `widget.git` (`github.com/acme/widget`). `project-id show` says so in `identity_detail`, and one warning per repository per process names that other id. If the remote is spelled the second way, write the pin without the trailing `.git` to share its memories.
- A pin line ends only at a newline (one carriage return before it is dropped); a control character such as `\x0b`, `\x0c`, `\x1c` or `\x85` inside or after the id refuses the pin (`control_chars`) instead of cutting it off.
- A remote-helper transport origin (the `<helper>::<address>` form, or `codecommit://`, `persistent-https://`, `sso://` or `keybase://`) has no portable id, so it uses its folder name as a repository with no remote does, a bucket shared with any same-name folder. `project-id show` reports `source` `remote helper` with that remedy in `identity_detail`, and one warning per repository per process names the remedy (a canonical id in `<git-common-dir>/pact-project-id`) without printing the url. `ftp://` and every other unknown scheme decline.
- A github.com remote with a one-segment path (`https://github.com/owner/.git`, `https://github.com/owner`) declines instead of binding `github.com/owner`: a github.com id is always owner/repo.
- A github.com remote whose path GitHub does not serve declines, in the memory id and the backlog alike: a home-relative path (`git@github.com:~/o/r`, `ssh://git@github.com/~/o/r`) and a non-bare repository path in any spelling (`/o/r/.git`, `/O/R/.GIT`, `/O/R/%2Egit`); a github.com remote whose path is not exactly owner/repo (`https://github.com/o/r/extra`) declines too, and so does an https remote whose `.git` suffix is escaped (`https://github.com/git/git%2Egit`), which GitHub does not serve; an `ssh://` remote decodes it (`ssh://git@github.com/git/git%2Egit` gives `github.com/git/git`). A plain ssh server still accepts both forms (`git@host:~/srv/repo` gives `host/~git/srv/repo` and `git@host:srv/repo/.git` gives `host/srv/repo`).
- A github.com remote on no port or its default port whose decoded owner or repo holds any character other than an ASCII letter, digit, `-`, `_` or `.` (an escaped `/`, `~`, `+`, a non-ASCII letter), or is only dots, gets no repository identity, and the backlog's slug check uses the same name rule, so the two always agree. The rule checks characters only: GitHub's other limits, such as no leading hyphen in an owner, are not checked, so `https://github.com/-o/r` still gives `github.com/-o/r`.
- A present but rejected pin in this repository no longer switches off url matching for sibling clones: only a usable pin does.
- A github.com remote ending in `.git.git` now drops one `.git`, as every other host does (it used to drop two).
- On an ssh remote, a path that starts with `~` is the login's home and keeps the login in the id: `alice@box:~/proj` and `ssh://alice@box/~/proj` give `box/~alice/proj`, as `~alice/proj` does from any login, and two logins' homes are two ids. A repository at the home itself is the login's too (`alice@box:~` gives `box/~alice`), while `alice@box:~.git` names the home of a user called `.git` and gives `box/~.git`. The login in an `ssh://` url is read percent-decoded, as git logs in with it (`ssh://al%69ce@box/~/proj` gives `box/~alice/proj`); a login an id cannot hold (a space, `%`, a non-ASCII letter, `.` or `..`) leaves the home unnamed (`box/~/proj`). With no login, `box:~/proj` gives `box/~/proj`. So a path written with `~` gets a different id from the same directory written without it (`alice@box:proj` gives `box/proj`, and so does `box:proj`), though git reaches the same directory; a pin at `<git-common-dir>/pact-project-id` gives both spellings one id. Any other relative path and an absolute path give one id whatever the login (`alice@box:proj`, `bob@box:proj` and `box:/proj` are all `box/proj`), because on a forge the path does not depend on the login. On a plain ssh server those can be three repositories; a pin at `<git-common-dir>/pact-project-id` gives each its own id.
- The remote is read with `git config --local --includes --show-origin -z --get-all remote.origin.url`, and the first value from the repository's own config file is used, so a machine-local `insteadOf` rewrite does not change the id. A url that only an included config file sets refuses, because it can change with the branch.
- Every route that resolves an identity runs the same guards: a `.git` file, symlink or admin pointer naming another repository's git directory, a submodule admin directory whose `core.worktree` (read from that admin directory's own config only, never global or system config) is unset and git does not name this folder as its working tree, a bare repository, and a `.git` git refuses to read. `.git`, `gitdir` and `commondir` files are read as git reads them, at most 1 MiB, never through a FIFO. An inherited `GIT_OBJECT_DIRECTORY` is ignored, like `GIT_DIR`, `GIT_WORK_TREE` and `GIT_COMMON_DIR`, so git and the marker walk judge the same folder.
- A `.git` file that redirects to another repository is caught even when an empty `.git` folder sits below it (`sub/.git/`): git walks past a folder that is not a git directory, and so does the marker walk, so from `sub/` the redirect declines (`gitfile_redirect`) instead of binding the other repository's id.
- The legacy-bucket case check no longer counts a symlink at the other-case folder name as proof that the filesystem ignores case, so a planted link cannot pull another project's folder-name bucket into the read scope.
- The location-divergence warning no longer names a dotfiles repository's id when the session runs under a HOME that is a git repository; it compares against HOME's folder name, as the resolver binds there.
- A home directory that is a git repository keeps its folder name and a warning, as before. A user-scope `project_id` in the memory `config.json` answers only when nothing was declared and no repository was found, whatever store `--db-path` names.
- Worktree listings are read with NUL separators, or checked field by field on a git older than 2.36. An older git that lacks an option refuses rather than falling back to a folder name. `GIT_CEILING_DIRECTORIES` and folder names holding newlines or trailing spaces resolve as git resolves them.
- The user-scope memory `config.json` is read like the other identity inputs: only a regular file, never through a symlink or a FIFO, at most 1 MiB; anything else is ignored rather than followed or waited on.
- Each git question is asked once per command.
- A repository whose origin URL has a non-ASCII digit in its port (a superscript two, for example) no longer makes every memory command fail with `SYSTEM_ERROR`; the identity declines instead.
- A user-scope `config.json` or a session record whose JSON nests deeper than Python can parse is skipped as unreadable, instead of failing memory commands with `SYSTEM_ERROR` ("maximum recursion depth exceeded").
- A `GIT_DISCOVERY_ACROSS_FILESYSTEM` value longer than 4300 digits is read as an invalid boolean instead of raising.

### Store, search and rekey

- Every project-scoped read takes the read scope, not one id. Text reads stay one SQL statement, so `LIMIT` and `OFFSET` apply to the merged result. Vector search runs one query per id and returns at most `--limit`. An empty scope matches no rows.
- `search` confirms each vector hit against its stored project and widens its fetch only up to 200 candidates, so on a store where many vector rows belong to another project (a rekey that could not move its vectors, or a copied store) it can return fewer than `--limit`, or none, while matching memories exist.
- Rekey merges file rows that collide on `UNIQUE(path, project_id)` and copies vectors by blob. When the target already links a memory to the same file with another relationship, the target's link is kept and the moved one is dropped and counted in `links_conflicted`; the move still completes. Its counters (`links_repointed`, `links_conflicted`, `vectors_moved`, `from_bucket_empty` and the NULL-row counts) are exact on a dry run, which never creates or initialises a store.
- The first memory read on a new derived store now answers empty and leaves the store with its schema, even when the embedding catch-up is skipped for the session.
- Read-only memory reads no longer open a store immutably while a rollback journal (`-journal`) from a crashed writer is present.
- A legacy bucket's rows and recorded sessions in another clone of the same repository no longer count against it: a checkout outside this repository whose `.git` is a directory is the same owner when its usable pin (read by the same rule as this repository's own: a BOM, blank and `#` comment lines, surrounding spaces and CRLF are accepted) is this repository's id or, when it has no usable pin, its own config's first origin url is this repository's origin url, written the same way (a url is compared only when this repository's id came from a url). The check reads files only and reads every line of the clone's config, so a clone with a differently spelled url (ssh against https, or with or without `.git`), a config holding an include, a dotted section header such as `[remote.origin]`, or an empty or valueless origin url anywhere in it, a linked worktree or separate-git-dir checkout of another clone, or an unreadable checkout stays a rival.
- A memory linking a file in another git checkout no longer hides or blocks the bucket: only a checkout named like the bucket counts as its rival owner.
- A warning or refusal that prints a `project-id rekey` command says the command previews the move and that adding `--apply`, with the user's approval, performs it; the printed command never carries `--apply`.
- A `project-id rekey` dry run no longer opens the store for writing: it plans on a temporary copy of the store file, which it then deletes, so the store file and its journal files are left exactly as they were. When it cannot write that copy (no usable temporary folder, or a full one), it fails as `REKEY_FAILED` (exit 3) naming the folder, and leaves the store and its folder as they were. A `TMPDIR` that is missing or not writable is not an error: Python skips it for the next usable folder (`/tmp`, then `/var/tmp`, then the working folder), and the dry run runs there. A disk fault that the store itself raises (its pages no longer read back) is reported as a store fault naming the store, not as the temporary folder's.
- `project-id rekey --apply` no longer prints the legacy-bucket read notices before its own result; a dry run still prints them.
- `project-id rekey --apply` refuses a canonical `--to` that is not this checkout's own id as bad input (`INVALID_INPUT`, exit 2) and moves nothing; a dry run still plans the move. To rename a repository's bucket, run the rekey from a checkout whose origin or pin already names the new id. `--into-another-repository` allows the move, only with the user's explicit approval.
- A defaulted rekey of this checkout's own pre-upgrade bucket that holds file rows but no memories is refused (`REKEY_REFUSED`): nothing verified those rows, so pass `--to` explicitly.
- A legacy folder-name bucket holding rows from this repository and from another checkout of that name is no longer read whole or moved by a defaulted `project-id rekey` for a repository-identity session; it is reported unproven (`foreign_rows`) with the number of foreign file rows. A bucket written only by sessions recorded at another existing folder is now excluded with no rekey command, and the warning names whether its foreign rows lie in another checkout or in another project folder of the same name.
- A file row under this checkout places a legacy bucket here only if its file still exists, or a memory linked to it was saved after the repository's `.git/description` last changed (a clone or `git init` dates it). An unrelated repository cloned into a deleted project's folder therefore finds that project's bucket unproven, not verified, and a defaulted rekey does not move it; a re-clone of the same project is still verified, since its files exist again. A repository with no `description` file counts its rows as before. A file that exists counts even beside missing rows, so a re-clone whose one file was renamed upstream stays verified; an unrelated clone that shares a file such as a README with the deleted project still finds the bucket verified, as every same-named folder shared it before this change. Judging the bucket resolves each folder of its file rows once and skips the date query for a file that exists, so a 5,000-row bucket adds about 0.11 s to a command instead of about 0.27 s.
- A canonical bucket of this repository under an earlier id (the origin renamed, transferred, or spelled another way, such as an ssh alias) is still not read. It is named only when a file row in this checkout is linked by one of the bucket's own memories (another bucket's memory linking the same file does not count) saved after the repository's `.git/description` last changed, every existing absolute file row of the bucket lies in this checkout (none in another checkout, outside it, or in a checkout nested in it; a row in one of its submodules is skipped, so a submodule is never named and does not hide its superproject's earlier id; a named bucket with such a row gets no rekey command, its notice leaves those rows out of the linked count and says how many lie in a submodule, since a whole-bucket rekey would move them too), and the bucket holds memories; a file that merely exists here never counts, so another repository's bucket that shares a README or links one file here stays silent. Then a read prints one notice per process (a quiet `rekey --apply` read does not use it up) saying how many of its own memories link files in this checkout and that it may be this repository under an earlier id, with the rekey command that previews the move into this checkout's id (add `--apply` with the user's approval; `--into-another-repository` is not needed, since the target is this checkout's own id), and `project-id show` lists it with relation `earlier_id` and that command. A bucket with an existing row in a linked worktree outside the repository root is not named. A checkout with no `.git/description` names no earlier id, since nothing dates its clone. A bucket with no row here linked after the clone, or with an existing row outside this checkout, costs a read no git call.
- The legacy-bucket session check no longer slows every memory command on a large sessions folder: at 3,665 session folders it took about 0.5 s per command and now takes under 0.1 s.
- Text search on a memory store that has no tables yet now returns no results instead of failing with an SQL syntax error.
- A store that is not a SQLite database gets a named remedy from every command. The embedding catch-up checks the store first and waits for a due dimension migration.
- A session in a repository with a canonical id can no longer file a memory into a folder-name bucket, or change the session of a row stored in one.

### Hooks and agents

- `hooks/session_end.py` appends one line per session folder it deletes to `pruned-sessions.jsonl`, so the evidence for an old bucket outlives the folder. The ledger is trimmed to its last 1 MiB past 2 MiB, by writing a new file and renaming it over the old one, without dropping a complete line. A writer skips its line when another session end holds the lock for about one second; if a trim replaces the ledger while it waits, it reopens and waits again, at most eight times (about eight seconds in the worst case), rather than waiting indefinitely, and session records are read only as bounded regular files.
- A session recorded at the repository's root counts as evidence for a legacy bucket only when `<git-common-dir>/description` is older than the session's start, or the repository has none. A session folder that was cleaned up counts through the line `pruned-sessions.jsonl` recorded when it was removed; one removed before the ledger existed left no line, so a project written only by such sessions reads unproven until its rows are moved with `project-id rekey --apply`. A session's start is its first one: a resume or a heal records its own time as the start, so the time of the first event in the session's journal is used when it is earlier, and the prune ledger records that earliest start.
- A repository that was moved, copied, restored or cloned again, and a folder that is not a repository, can read its old folder-name bucket as unproven; the printed rekey command moves it, with the user's approval.
- `project-id rekey` no longer accepts an omitted `--to` for a legacy bucket read on session evidence alone, so one recorded session cannot move rows no session places; pass `--to` explicitly.
- A repository session's refused write into a folder-name bucket now reports `LEGACY_BUCKET_WRITE_REFUSED` (exit 2) without the unrelated field-validation note. A session whose identity declined at a live repository (an origin no id can represent, for example) is refused the same way, since it becomes a repository session once its origin is fixed; it may still save under a supplied canonical id. A declared directory that is gone, or a deleted working directory, is no repository and is not refused. `get` by its full id (a short prefix of such a row is `NOT_FOUND`), and an `update` that changes neither `project_id` nor `session_id`, still work on a row in a folder-name bucket the read scope does not cover.
- A `--separate-git-dir` checkout without a portable origin no longer silently drops its pre-upgrade bucket: the old bucket is disclosed as its legacy candidate, and `project-id rekey` can move it into the checkout's own folder-name id.
- A session launched in a subfolder of a linked worktree that sits inside its main checkout (for example `<main>/.worktrees/<wt>/sub`) counts as a subfolder launch again, not as another owner, so a repository with that layout keeps reading and saving its own folder-name bucket.
- Removing a linked worktree no longer pushes the repository's own pre-upgrade bucket out of reads with a false "another checkout" warning: a session whose recorded directory no longer exists counts as unattributed.
- A legacy bucket read on session evidence alone (`included_unverified`) that holds memories from no recorded session is read with a warning, once per process, that gives their count and the rekey preview. A `verified` bucket, placed here by its file rows, gets one informational line instead, which gives the count and says its rekey moves them with it.
- The session-end PR check and backlog issue refs accept only ASCII digits: a superscript or other-script digit is no longer read as a PR or issue number, and an over-long PR number no longer raises.
- A backlog command that succeeds prints no memory-identity warnings (a decline, a HOME landing, an ignored override, a remote-helper folder name), because the backlog keys on the folder name; it still prints the memory store's own warnings (for example, that the legacy project bucket could not be checked), and a refusal prints them all, in the order they were logged.
- `hooks/shared/backlog.py` records only worktrees whose `.git` and admin entry name each other, reads the listing with the memory skill's reader, and refuses with the memory skill's cause when the checkout cannot be confirmed.
- A bare repository whose `core.bare` is spelled `yes`, `on` or `1` is now recognised as bare by the CLAUDE.md project-root check, as git reads it.
- The CLAUDE.md migration drops an old memory-section comment only inside a memory section; a line reading the same in a user's own section is kept.
- The Working Memory comment in `CLAUDE.md` points to `project-id show` for the section's key and says nothing is written to that section when the identity declines; a section carrying an earlier wording of the comment is rewritten to the current one. The secretary reads the projection by `read_scope`, sends a null `project_id` to `project-id show`, and counts calibration records across every id in the scope.

### Tests

- New modules cover the remote grammar, every resolution route against real git layouts (forged pointers, submodules, separate git dirs, home checkouts, old git versions), the read union and the plausibility gate, rekey on a copy of a real store, read purity, and the agreement between the memory and backlog remote parsers. Prose arms bind each agent-facing clause to the code that emits it, including each documented exit code to a real CLI run.

### Why

The folder name is not an identity. One repository checked out under two folder names produced two unrelated memory buckets, and two unrelated folders that happened to share a generic name produced one shared bucket; both directions are silent, so a reader sees either an empty project or another project's memories. A repository's remote is the one name every checkout of it already agrees on, and it travels with a clone rather than with a path. The design keeps three properties a later change must not undo. First, this checkout's own legacy bucket stays readable by the read union, while its evidence holds, until an explicit rekey; there is no alias table, no redirect and no effective-id indirection, so nothing silently rewrites stored rows and a rekey remains the one action that moves them. Second, the backlog file name stays keyed by the folder name deliberately, because that value is a path component. Third, an identity that cannot be resolved or represented declines instead of falling back to a basename, because a basename is exactly the silent misfile this change removes.

## v4.8.38: arm a structural wait watcher instead of refilling the loop

### Summary

For a plugin user, a team-lead waiting on a teammate's deliverable no longer idles behind repeated no-op calls. It arms a bounded watcher as one background task the harness tracks: one `Bash` call with `run_in_background: true`, or, where `Bash` is reached only through a REPL that refuses that flag, the same command awaited with a short timeout (for example 3000 ms) so it moves to the background. Then it ends its turn. The watcher's exit re-invokes the lead when the deliverable lands, and fails loudly when the deadline passes or the watch cannot run. The plugin hands the lead the ready-to-run command whenever one of its writes leaves a teammate's deliverable due: a work task that is now live, owned by a specialist other than the lead and unblocked, a teachback gate that is now handed to its teammate, or a deliverable it has just rejected. The filler guard's last-tier denial now carries that command instead of the retired circuit-breaker valve. Two hooks (`task_lifecycle_gate.py`, `wait_filler_gate.py`) and four shared hook modules (`turn_end_gate.py`, `handoff_schema.py`, `task_utils.py`, `hook_infra_classifier.py`) change, and one helper (`pact_wait.py`) and one shared module (`wait_target.py`) are added. Six instruction files change: the orchestrator persona, the pact-agent-teams skill, the secretary agent, and the protocols file with its task-hierarchy and completion-authority extracts.

### What landed

- `hooks/pact_wait.py` (new) is the watcher: a stateless command-line helper, not registered in `hooks.json`, that the lead launches itself so the harness tracks it. It reads the team's task file before its first sleep and then every few seconds. It exits 0 when the deliverable is present, 3 when the deadline passes without it (its message tells the lead to re-arm or escalate), and 4 when it cannot watch at all: an unknown predicate, an unusable team or task id, or a task file that is missing, unreadable, unparseable or not a regular file (a FIFO or a device is never read, so it cannot hold the watch past its deadline) on two consecutive reads (one bad read is tolerated as a mid-rewrite); a symlink loop in the team's task directory also exits 4, never a crash. `--deadline` is required, must be finite and positive, and is capped at 86400 seconds; a bad value is a usage error (exit 2) before any watching, and so is a `--task` still set to the arm command's `TASK_ID` placeholder, a plain word that a shell run without substituting it cannot turn into a redirection. An uncaught exception exits 1 with its traceback, so a crash never reads as an expiry. Each exit message names the predicate, task and team.
- `hooks/shared/wait_target.py` (new) holds four things the rest of the mechanism shares. The predicate registry: `handoff` (a `metadata.handoff` whose `produced` is a non-empty string, or a list holding one, so a handoff in the flagged list shape still wakes the lead) and `teachback_submit`. Both stay unsatisfied while a `handoff_rejection` or `teachback_rejection` covers the revision on disk, so a watcher armed after a rejection waits for the revised submission instead of firing on the rejected one. The one arm-command builder every emitter uses, which shell-quotes each value. The one classifier of a running watcher's command, which accepts every form the builder emits. And `wait_identity`, the one source of the team an arm command names, which both producers call: the live task store the session context resolves to, or, for a frame with no session context (a separate-process teammate), its registry team when that team's task store exists. A frame that has a session context but no resolvable store gets no command. Membership and role are read under the frame's own team, which can differ from the store's name when a session has no team config. Every wait-path consumer takes its team from it: the lifecycle gate reads tasks under the store team and owner roles under the membership team, and its revision advisories (including a separate-process teammate's own) use the store team. The module also owns the one parser of a revision number, which those revision advisories read through, so they cannot describe a revision differently from the watcher.
- `hooks/task_lifecycle_gate.py` supplies the arm command as a PostToolUse advisory from one readiness rule. A work task is ready for a `handoff` watch when it is pending or in progress, is not a teachback, is owned by a specialist other than the lead or the secretary, and has no unfinished blocker; a teachback gate is ready for a `teachback_submit` watch when it is pending, has an owner other than the secretary, and has no unfinished blocker; at a blocker's completion, a gate its teammate already claimed also counts while it has no `teachback_submit`. The rule is checked only at the lead writes that can make it true, and only when the write actually changed the relevant field: an owner change (per the harness's `updatedFields`), a `TaskCreate` with an owner (for either, a blocker the same write adds counts as unfinished), a completion that moved a task into `completed` (per `statusChange`; the completed task's dependents are found from its record and a scan of the store for tasks it blocks), and a write recording a `handoff_rejection` or `teachback_rejection` on a live task. So a work task behind a teachback and a predecessor is armed when the last of them completes, in either order. Task ids are normalised to strings before any comparison. The same gate advises when a rejection's `revision_number` is not the revision being rejected (an omitted number is accepted at revision 1, which is how the watcher reads it), when a teammate sets `metadata.revision_number` to one above a rejection's without the revised deliverable in the same write (worded as a condition, because the hook sees only the state after the write), and when a teammate re-submits the deliverable without raising `metadata.revision_number` past the rejection's. Frames whose `agent_type` names a non-lead actor get no arm. The advisory also tells the lead, when the user may be away, to back the watcher with a recurring `CronCreate` check keyed on the deliverable. The gate only supplies command text; it never starts the watcher.

The last-tier denial is now always a denial, and its text depends on who is waiting. The texts are rendered from one table that maps each kind of wait (a teammate's deliverable, the reader's own write, the lead's action) to one action, and only the arming branch describes the watcher's exits. The lead and a separate-process teammate get the arm command with the team from `wait_identity`. When the lead or a teammate waits on something only it can write, the text tells it to write it now, because nothing wakes it later to write it. The lead's arming branch carries the same `CronCreate` backstop as the advisory. Every `intentional_wait` branch names the value to write: `metadata.intentional_wait` with `expected_resolver` set to `lead`. Every role also has a catch-all branch, so a wait that is neither a teammate's deliverable nor the reader's own write (a user reply, a message) still has an action: the lead and a separate-process teammate end the turn. An in-process teammate gets no command: it sets that wait and ends its turn, because a background exit does not wake it. An Agent-tool subagent gets no command: it ends its turn and puts what the lead needs in its final report. A frame whose task store does not resolve (no PACT team, or an ambiguous store) gets the stop instruction alone. The earlier tiers and the allow path are unchanged. The retired `valve_budget` field is ignored on read and always written as an inert `0`, whatever an older writer left there, so a session that falls back to the previous release mid-way reads the state file as valid and that release's retired allowance stays closed.
- `hooks/shared/turn_end_gate.py` stops counting a running watcher as unowned background work for the lead and for a separate-process teammate, whose own exit notice starts their next turn; a watcher a REPL moved to the background by a short timeout carries the same command and is matched the same way. An in-process teammate's watcher still counts. The match is strict: a command composed onto the watcher with `;`, `|`, `&`, a substitution or a line break between its arguments, or a partial invocation, still counts as work to account for, while an interpreter given by path, a leading `cd` or environment assignment, and a trailing `2>&1` are accepted. The lead's block text says a watcher is listed only when its command differs from the arm command's form, and is then accounted for like any other job.
- `hooks/shared/handoff_schema.py` flags a `produced` that is not a string, and separately one that is empty or whitespace only, since the watcher reads an empty one, and any value other than a string or a list holding one, as absent. The flag is an advisory at write time and at completion; it does not block. `hooks/shared/task_utils.py` gains the one task-id sanitizer that the task reader and the watcher share, and its task reader now returns no record for a file holding JSON that is not an object, so a list in a blocker's file no longer fails the lifecycle gate for the turn. `hooks/shared/hook_infra_classifier.py` adds `wait_target` to the recorded helper import closures of the hooks that now import it.
- Instruction files: the pact-agent-teams HANDOFF template, the secretary's memory-save HANDOFF example and the protocols metadata example (with its byte-compared task-hierarchy extract) now show every HANDOFF field as a string. The orchestrator persona's wait discipline puts teammate-deliverable waits inside the watcher scope (arm before ending the turn, running the command the lifecycle gate's advisory or a filler-gate denial supplies), backs such a watcher with the deliverable-keyed cron whenever the user may be away, and limits the do-not-background rule to in-process teammates. The pact-agent-teams wait discipline adds one exception for a wait on another teammate's deliverable: a separate-process teammate arms the watcher only with the command a filler-gate denial gives it and otherwise sets `intentional_wait` naming the lead; an in-process teammate sets `intentional_wait` instead; an Agent-tool subagent does not arm. The persona's watcher launch, both of these arming instructions and the QA engineer's dev-server start now launch the job as one background task the harness tracks: one `Bash` call with `run_in_background: true`, or, where `Bash` is reached only through a REPL that refuses that flag, the same command awaited with a short timeout (for example 3000 ms) so it moves to the background. A PreToolUse hook cannot end a model's turn: a denial and an allowance each produce another turn, so text telling the model to stop was never terminal, and the circuit-breaker valve did not stop the loop it sat inside. The one path that reliably re-invokes an idle lead is the exit notice of a background task the lead launched itself. The mechanism moves the wait onto that path and keys it on the awaited deliverable in the task file, not on a file time or other side signal. The plugin supplies the command rather than only teaching it, because running a concrete command is easier for a waiting model than refraining from tools.

## v4.8.37: hold in-process teammate idles briefly for a crossing wake

### Summary

When an in-process teammate goes idle within a few seconds of setting an `awaiting_lead_completion` wait, the `TeammateIdle` hook now holds that idle for up to 10 seconds from the wait's anchor. It returns as soon as a valid, unread message for the teammate is in its inbox, so the runtime can deliver that message as the teammate's next prompt before it announces an idle that the message has already resolved. The hook never blocks the idle, sends nothing, and writes no task or inbox state; with nothing queued it returns the ordinary idle output at the deadline. The completion-authority protocol and the agent-teams skill now limit the old "no synchronous wake hook" non-goal to the lead's send path and permit this receive-side hold.

### What landed

- `TeammateIdle` hold: it applies only to in-process teammates, and only while the teammate's own `in_progress` or `completed` task carries a valid `awaiting_lead_completion` wait less than 10 seconds old. The age is measured from the wait's `covers_since`, so re-stamping `since` alone does not restart the budget while `covers_since` is kept; a wait without `covers_since` is keyed on `since`, so each re-stamp gives it one more 10-second budget, and a `covers_since` that is present but unreadable means no hold. A wait timestamp truncated to the whole second, as `canonical_since` writes it, can make the window up to one second shorter, never longer. A new shared helper, `background_work.teammate_is_in_process`, decides the mode by reading the team config through `state_file`, only for an idle that has an eligible wait (at most 1 MiB, and contained under the teams root, so a team directory linked outside it counts as no config); pane and tmux teammates, and any teammate whose mode cannot be confirmed, are never held, because a pane teammate's idle notification is sent before this hook runs. A held idle polls the inbox every 0.1 seconds. It counts only an entry not marked read with clean, non-empty string `from` and `text` fields; a malformed entry is skipped without hiding a valid one beside it. An unsafe team or teammate name means no hold at all; once a hold has started, a non-list document, an oversized file or a path the containment check refuses ends it at once. A missing inbox, unparseable JSON (including a document nested too deeply to parse) or text that fails strict UTF-8 decoding (such as a half-written non-ASCII message) is retried until the deadline; undecodable text never counts as a message. When a hold ran, the hook re-reads the team's tasks before idle cleanup and the background-work advisory, so a task that changed during the hold (for example one the lead completed) is judged in its current state. Whatever the hold finds, the hook then returns its ordinary output; an unexpected error during the hold is reported as a single printable stderr warning line, with non-printable characters (line breaks, a bell, or the escape character that starts an ANSI sequence) turned into spaces and the error text capped at 200 characters, with the hook's output and exit status unchanged. `hooks.json` lowers the `TeammateIdle` hook's timeout from the 600-second command-hook default to 20 seconds, which still covers the hold.
- `state_file.read_text` gains a keyword-only `strict` option that raises on invalid UTF-8; the default is unchanged. Reads and appends walk the checked directory from the root descriptor without following symlinks, so a path component swapped for a symlink or a non-directory after the containment check is refused; a refused read raises the public `state_file.Refused` (a `FileNotFoundError`), so a caller such as the hold tells it from a missing file by type. Any other error on that walk (permission denied, too many open files) is raised unchanged, as a plain path open raises it, and where `O_PATH` exists (Linux) directories are opened with it, so search permission is enough, as before; elsewhere (macOS) they open read-only and need read permission.
- `pact-completion-authority` (and its `pact-protocols` mirror) narrows the synchronous-hook non-goal to the lead's send path and permits a brief receive-side `TeammateIdle` hold for in-process teammates; the redundant-confirm procedure is unchanged. The `pact-agent-teams` skill says the same in one sentence. Pins hold the new wording and fail when it is deleted, its meaning flipped, or mechanism detail such as the time budget copied back into the prose.
- Tests: an end-to-end test runs the real `TeammateIdle` hook as its own process against a temporary config directory with a real task file and inbox, proving the hook finds the teammate's inbox through its own path resolution. Each arm first times the same hook with no hold to measure this machine's start-up, then keeps about 8.5 seconds of the window (9.5 for the message arm) and checks three seconds past that start-up: a message that lands then must end the hold within two seconds, and that arm requires room for those two seconds plus a margin before the deadline, so a hook that never reads its inbox cannot pass by running to the deadline; a hold with nothing queued must still be running then and last to the deadline, and a tmux teammate must return within three seconds of start-up. A hook with the hold removed exits at start-up, so it fails even when its own run starts up to about 2.5 seconds slower than the measured one; if start-up leaves no room for the check, the arm fails before launching anything, with a message saying the runner is too slow, rather than passing. Fake-clock tests cover eligibility, the deadline, retries and fail-open inputs; they also prove the unsafe-teammate-name guard and check the hook's actual output, not its source text, for the absence of a decision on every hold path, using a fixed clock for the deadline case so a slow machine cannot skip the hold. A spawn-overhead control proves the shared completion-authority note is counted. The test bootstrap now imports `peer_inject` with the other by-value importers, so the import-order census covers that note, and an autouse fixture makes any in-process test that reaches the hold's real sleep fail at once, so a regression that widens eligibility cannot turn tests into 10-second waits.

### Limits

- The hold helps only when the teammate's idle fires inside the window after it sets its wait; how often that happens in practice is unmeasured.
- A task the lead has already completed, whose wait the teammate has not yet cleared, can be held for up to the rest of its window when the lead's reply has already been read, because nothing unread is left to end the hold early.
- An eligible idle with nothing queued is delayed by up to its remaining budget. That covers most teachback and handoff waits, since a lead usually answers after the budget has passed.
- If the held turn ended with plain final text rather than a message to the lead, the runtime still sends an idle-type notice after the hold.
- Whether the runtime waits on `TeammateIdle` hooks in a way that could serialize other hooks during a hold cannot be determined from the code and is unmeasured.
- One live in-process probe measured the hold. A lead message sent six seconds into the wait ended the hold early, and the lead got no "available" idle notice, only the plain-text-turn notice above. With nothing queued, the "available" notice came at the deadline. An unpatched baseline crossed: its notice arrived before the message was sent. That is a single run, not a rate. Pane teammates are never held by design, and a wake can still cross an idle outside the window; the lead's redundant-confirm procedure still covers it.

### Why

Crossed wakes made leads read a teammate's idle as needing attention when the lead's own message was already on the way. Instruction-only wording did not stop that narration in live probes, so this change moves the control to event ordering. An in-process runner checks its mailbox after the `TeammateIdle` hook and before it announces the idle, so a message that lands during a short hold can be delivered before the idle is announced. A `decision:block` was rejected: it does not deliver the queued message, and every block adds a model turn. Requiring positive evidence means an empty or half-written inbox never counts as a message, and the fixed age bound means a hook can never hold an idle indefinitely. Ten seconds is a starting value, not a measured optimum.

### Shuffled-order diagnostic runs

- `constraints-ci.txt` pins pytest-randomly 5.1.0, and the root `pyproject.toml` blocks it with `addopts = "-p no:randomly"`, so the merge-queue gate, the fast suite and every local run keep file order. The pytest children the suite starts pass `-p no:randomly` themselves, because a child rooted outside the repository does not read the root config. The full-collection guard's own collection run passes it too: in CI it runs inside the repository, but the suite's own tests run the guard in temporary checkouts with no root config.
- A test session refuses to start when pytest-randomly is loaded without an explicit integer `--randomly-seed`, whether it was loaded by its entry point or by its module name (`-p pytest_randomly`). Losing the `pyproject.toml` block, unblocking it, or shadowing it with a nearer pytest config file therefore fails the run instead of shuffling it. The check runs from `pact-plugin/conftest.py`, so it covers every session that collects a path under `pact-plugin/`, skills-adjacent tests alone included; a `--noconftest` session, or one collecting nothing under `pact-plugin/`, is not gated. Each xdist worker checks its own invocation as well, so a run started from the repository root, where only the workers load that conftest, is gated too. Arguments read from an `@file` count as pytest reads them, one per line. A seed written after a bare `--` counts, because pytest applies it when no path precedes the `--`. A seed counts when pytest-randomly reads it as an integer, so `+5`, `-5`, `5_0` and `007` count; its special values `last` and `default` do not, because they name no seed the run line records.
- The full-suite workflow takes an optional `shuffle_seed` dispatch input.
  - A guard accepts only an empty value or a decimal seed of up to 9 digits with no leading zero, and refuses anything else before setup.
  - A seeded run shuffles the suite and passes `--randomly-dont-reset-seed`, so pytest-randomly does not reseed the random generators before each test; it still seeds them when each process starts its session and again when it shuffles. Every process gets the same seed, so every xdist worker starts from the same random state and makes the same first draws from the global generator, which an ordered run's workers never do; a test that picks a port or a temporary name from that generator could collide across workers only in a seeded run, and the comparator would report the collision as an order effect.
  - The evidence artifact name ends in `ordered` or `seed-N`.
  - The seed travels in the job-level variable `PACT_SHUFFLE_SEED`, job-level because the test step reads it on its run line and may not carry `env:`; the full-suite comparator accepts the seeded run line only under that name.
  - Merge-queue and push runs pass no seed, so their pytest command is unchanged.
  - On Linux the guard's test also checks non-ASCII digits under a locale it builds, and fails in CI if it cannot build it.
- `scripts/compare_full_suite_results.py` reads each run's seed from the full-suite step's own pytest-randomly header and records it beside the run identity, outside the compared environment, so a shuffled run compared with an ordered one reports a real test difference as a delta.
  - A seed or census line printed in a test's captured output is ignored. So is every other evidence line a test prints: the comparator reads the run command, the environment-check and verifier lines, the CI binding's drift heading, the PYTEST_ADDOPTS refusal and the environment axes only outside pytest's report sections, and XPASS lines only from the short test summary's XPASS entries, which -ra prints before any error or failure entry, so a failing test whose output or CI failure message carries one of them is still compared as a failing test. A SKIPPED entry is matched to the skip reason it prints whole, so a reason that ends another reason's first line cannot be taken for it. A CI failure message can hold a child pytest's whole report, its own short test summary header included, and so can a failing test's captured output, and the log alone cannot tell such a header from pytest's own. So a log with more than one short test summary header is refused, with a reason that says so, even when the run is a valid red run whose failure message holds a child pytest's report. A log with one header has that summary read, and a summary that does not read cleanly refuses the run.
  - It refuses as evidence a log with two seed lines, a seed line beside the unseeded run line, a seed line whose value is not 1 to 10 ASCII digits (a sign, `last`, an empty value or trailing text included), a log with no session banner after the run command, a seeded run line without `--randomly-dont-reset-seed`, a pytest-randomly seed line in the test step's log outside the report header, a log whose only matching summary line comes before the session-finish span ends, and a header seed that disagrees with the seed the test step's environment echo names (empty for an ordered run, with or without the runner's trailing space), so a seeded run is never read as ordered.
  - A test runs a real seeded pytest-randomly session, serial and under xdist, and requires the comparator to read its seed from the real report header and the seed gate to find the plugin loaded; it skips locally without pytest-randomly and fails in CI without it.
- It reports a green run that a census failed as a census outcome naming the census, and a red run still records any census that failed it. It refuses a census failure beside exit status 0 or beside a status a census cannot produce, a red run beside exit status 3, 4 or 5, which a test failure does not set, and a census block whose problem lines do not match its header's count. A census that failed both runs but names different tests, or the same test with a different problem, is reported as a `census_tests` delta; each test is compared with its problem, without the worker prefix, the launch text and the working directory, which hold temporary paths, and a problem line that names no test is compared by its problem, the text before its first `: ` (a colon and a space), because its counts and paths also differ by run. A census header that appears twice in the session-finish span is refused, since each census prints it there once per session. A census problem line is census evidence only: the pins and measurements environment axes do not read it, so a launch it quotes that names `constraints-ci.txt` or `sys.executable=` is a census delta, not an environment difference. `comparison.json` and every `runs.jsonl` record move to schema_version 2, which includes the `census_tests` delta type.
- The CI workflow's header now says why ordered and shuffled runs share one environment: they then differ in test order and in the random state pytest-randomly seeds from `shuffle_seed`, never in the installed set, so the comparator attributes any difference between them to the order or to that seeded random state. A seeded run sets each process's starting random state from the seed, while an ordered run starts from fresh entropy. The environment check holds both runs to the same lock.

### CI package lock

- `constraints-ci.txt` is now a hash-checked lock generated from the hand-edited `constraints-ci.in`: every distribution, pip included, is pinned with a sha256 hash for each file. CI installs it with `pip install --only-binary=:all: --require-hashes -r constraints-ci.txt`, so a missing pin, a changed file or a source build refuses the install. `.cursor/install.sh` installs the same lock but still accepts source builds (pysqlite3 has no aarch64 Linux or x86_64 macOS wheel) and says so. The environment check parses the lock and version-checks pip like any other pin. Its install remedy prints the CI line in a GitHub Actions run, and elsewhere prints the local line with the source-build risk stated beside it.
- The lint gate's ruff-missing remedy installs ruff alone into the repository's `.venv`: it copies ruff's own entry, with every hash, out of `constraints-ci.txt` and installs it with `--require-hashes --only-binary=:all: --no-deps`, so the version is CI's and nothing is compiled, since ruff publishes wheels for Linux, macOS and Windows; `.cursor/install.sh` remains the full environment. The printed commands are one command for a POSIX shell, each step joined to the last with `&&`, so pasted as a block they stop at a failed step, the floor check included, and never install into a venv below the floor; on Windows the same steps use `.venv\Scripts\python` and `.venv\Scripts\activate`. It no longer installs into whatever `python3` is first on PATH. When `.venv` already exists, the remedy keeps it: it checks the floor with the venv's own interpreter and never runs `python3 -m venv` over it, which would re-initialise the venv with whatever `python3` is first on PATH. When `.venv` is a link to a directory that does not exist, the remedy prints no command that installs into it or creates anything over it: it says the link is broken, names its target, and says to restore that venv or to remove the link with `rm .venv` and run the gate again for the commands that create one. Tests pin the printed text for all three cases, run the printed extraction against the lock, and run the real gate with no ruff on PATH, requiring exit 2 and the script's own remedy text.
- The local lint gate's ruff-missing remedy refuses a `python3` below the interpreter floor before it creates the venv, with an explicit exit that `PYTHONOPTIMIZE` cannot skip, and a test holds its floor equal to `.cursor/install.sh`'s and the declared `requires-python`.

### Test-suite censuses

- A child-pytest census refuses a pytest child the suite starts when that child would load pytest-randomly, for the launch families its docstring lists: pytest's own program, `coverage run`, an interpreter's `-m pytest`, an interpreter running pytest's script, and any of these inside a shell's `-c` text.
  - A pytest child started through any other program (`timeout`, `sudo`, `uv run`, or such a program run as an interpreter's module, `python3 -m uv run`) is refused whether or not it blocks the plugin, with a line naming that program and the remedy, since the census cannot tell what such a program passes on; the census follows a chain of known wrapper names (`timeout 60 nice pytest`), and `find`'s `-exec` actions, to the program they start.
  - It judges a child by replaying pytest 9.2's own plugin loading over `-o addopts=`, `PYTEST_ADDOPTS` and the argv, so autoload left on, a name in `PYTEST_PLUGINS`, a module-name load and `--disable-plugin-autoload` count as pytest counts them.
  - It judges the program a launch runs, not the name it shows: `subprocess`'s `executable=` (with `shell=True`, the shell) and `os.posix_spawn`'s path take the place of `argv[0]`.
- The child-pytest census reads every shell's `-c` text by bash's rules, including comments (inside `$( )` too, so a quote or paren in a comment there does not move where it ends), heredocs, command substitutions and redirections; a substitution nothing closes is judged whole and refused on purpose, as text bash rejects is; it does not perform brace or pathname expansion, so `{pytest,-q}` and `/venv/bin/py*test -q` are listed blind spots.
  - Text bash cannot parse is still judged by those rules, so it is refused only when, read that way, it runs an unblocked pytest.
  - Commands that only mention pytest are not refused, such as `git grep pytest`, `pip install pytest`, `grep -c pytest log` or `ls -la pytest`. A program that prints, reads or lists its words (`grep`, `rg`, `ls`, `cat`, `sed` and the like) is never taken to run them, while `xargs` and `find`'s `-exec` are read for the command they run.
  - A command whose program prints, reads or lists its words (`echo`, `printf`, `grep` and the rest of the census's run-nothing list) is not read for an interpreter's `-m pytest` among those words, so `printf '%s\n' python -m pytest` and `git grep python -m pytest` are mentions; the next command in the same shell text is still judged.
  - The mention stop applies only to a word in program position (the program, the command a listed wrapper runs, or git's subcommand), so `make test python -m pytest` is refused while `git grep python -m pytest` stays a mention.
  - File commands (`chmod`, `chown`, `touch`, `mkdir`, `rm`, `cp`, `mv`, `ln`) and `[[`, `type` and `hash` join the programs that never run their words, so `chmod 755 /venv/bin/pytest` is accepted.
  - A harmless command the census still refuses is an accepted, documented limit: it fails loudly with a remedy. `python-config -m pytest` is refused as a launch through a program the census does not read, and the line names that program; `make check python -m pytest` gets the ordinary does-not-block line, which names no program, and `-p no:randomly` lifts it.
  - The mention stop follows a wrapper chain into git's subcommand, find's first `-exec`-family command and the `command`/`builtin` builtins exactly as it reads them without a wrapper. So `timeout 5 git grep python -m pytest` and `find . -exec echo python -m pytest ;` are mentions and a find with no `-exec`-family action runs nothing, while `timeout 5 git pytest` and `timeout 5 command pytest` are refused.
  - The census judges the command three git subcommands run: `git bisect run`'s command, and the shell text of `git submodule foreach` and `git rebase --exec`, in every form git 2.43 runs: `--exec` and its prefixes `--ex`/`--exe`, and `-x` alone or ending a bundle of short flags (`-ix`). So `git bisect run pytest` is refused and `git bisect run make test` is not; git's other ways of running a command are listed as blind spots.
  - The command `git submodule foreach` runs takes the program position, followed along a wrapper chain as for `git bisect run`, so `git submodule foreach echo python -m pytest` is a mention. A `git rebase --exec` value is one word, so the words after it are rebase's own arguments and are read as any unknown program's are.
  - The launch aborts before the child starts.
  - A launch the census cannot read fails the run only when one of its words names pytest as a program or module (pytest's program wherever it stands, `pytest/__main__.py`, or `pytest` after `-m`, a short-option cluster ending in `m`, or `--module` in a command that names an interpreter or `coverage` before it, so git's `-am` in `git commit -am pytest.__main__` is not read as `-m`; or coverage's module, the first plain word after its options, as in `coverage run -m -p pytest.__main__`), not when a word merely contains it, such as a tmp_path under `/tmp/pytest-of-<user>/`; its line names the test. It splits shell text as its shell reader does, so pytest's name written against an operator (`cd x&&pytest`, `pytest;echo`, `(pytest)`) or inside backticks still fails the run.
  - A test fails when `constraints-ci.txt` pins a pytest or pytest-randomly major.minor other than the one whose plugin loading the census replays (9.2 and 5.1), and names what to re-check, so a lock refresh cannot silently change what the census accepts; the CI environment binding already holds CI's installed versions to the lock.
  - A differential test runs each of the census's plugin-loading rows as a real pytest session wherever pytest-randomly is installed, and fails when a real session disagrees with a row or when no row both loads and blocks the plugin. In CI, which installs the lock, a missing plugin fails it, so a pytest patch release that changes plugin loading cannot silently change what the census accepts.
  - The census is installed from `pact-plugin/conftest.py`, as the HOME census is, so a session of `pact-plugin/skills/` tests alone refuses an unblocked pytest child too, with exactly one census per session; `tests/conftest.py` wires only the clock-shift census.
  - The census reads the Windows launcher's `-V:<tag>` and `-3.12-<arch>` as one option, so a tag holding an m or a c (`py -V:Anaconda3/3.12 -m pytest`, `py -V:ContinuumAnalytics/3.12 -m pytest`) is judged like `py -V:3.12`.
  - pytest's numbered temp root (`pytest-N` directly under `pytest-of-<user>`) never names pytest's program, so `rsync -a src/ <basetemp>` is accepted, while a distro `pytest-3` still counts. git's subcommand is the first word past git's own options, where `-C`, `-c`, `--git-dir`, `--work-tree`, `--namespace`, `--config-env` and `--attr-source` take the next word as their value, so `git --no-pager grep python -m pytest` is a mention.
  - The census reads bash's `$'...'` quoting as the word bash builds, escapes included, and `$"..."` as a double-quoted string, so `bash -c "$'py\x74est' -q"` is refused unless it blocks pytest-randomly.
  - `$'...'` is one quoted span inside command and process substitutions and arithmetic too, and a `$'...'` or `$"..."` heredoc delimiter is the word bash uses, so an escaped quote or such a delimiter cannot hide a later unblocked pytest.
  - A test runs each shell-text row the census's tables say bash was measured on under real bash with only stub programs on PATH, and fails when bash's behaviour disagrees with the row, so the census and a row cannot be changed together into a verdict bash contradicts; it skips below bash 5.2 and fails in CI if it cannot run.
  - Launch forms outside those families are not seen; the docstring lists examples.
- A runtime HOME census replaces the static home-isolation scan.
  - It refuses a child launched with an environment that has no HOME key, or one that inherits the suite's environment while that has no HOME, because such a child finds the real home through the password database. A refusal aborts the launch and names the test.
  - The only exemption is `@pytest.mark.child_env_without_home(reason=...)` with a non-empty reason, and it is in force for the marked test's whole setup, call and teardown, its function-scoped fixtures and any hook that runs during them included, never for a wider-scoped fixture's setup or teardown, nor for a finalizer registered on a wider node (`request.node` or `request.session` `.addfinalizer` in a wider-scoped fixture), which runs in the teardown of whichever test is last in that node, so the verdict does not depend on test order. The report hooks of the marked test's teardown phase count as its own whether or not a wider node tore down just before them, so they too do not depend on test order.
  - A clean run prints `HOME CENSUS: installed, N launches checked, 0 refused`.
  - A worker that crashes before its census finishes is a listed blind spot: a refusal a test there swallowed is not reported, and that worker's launches are missing from the launch count; a refusal no test swallowed still fails its own test.
  - Under xdist the HOME, child-pytest and clock-shift census reports start on their own line rather than after the last progress marker; the comparator reads both forms.
  - The child-pytest and HOME census refusal headers say `distinct`: an identical refusal line is recorded once, so the number counts distinct refusals, not launches. A refusal stops its launch at the first audit event, so the lines merged are those of repeated identical launches. A launch a census cannot inspect is not stopped and can raise two audit events, `subprocess.Popen` then `os.posix_spawn`, whose identical lines are merged too.   - A test that does not run in a session is judged on the machine where it does run, in any session that loads pact-plugin/conftest.py, and a launch it makes there that the census refuses is stopped before the child starts.
- The HOME census is installed from `pact-plugin/conftest.py`, which every session under `pact-plugin/` loads, so a session of `pact-plugin/skills/` tests alone is censused too, with exactly one census per session. ### Root conftest import charter

- `pact-plugin/conftest.py` states its import charter: at any scope it imports only the standard library, pytest, and tests/ modules whose own imports, followed through every tests/ module they reach, are only those. It makes no dynamic import except two named, gated ones: the CI environment check's script load, which imports `packaging`, only when GITHUB_ACTIONS=true, and the import-identity map's find_spec, only when PACT_IDENTITY_MAP_OUT is set. It forbids any helper that imports a module by name.
- A pin enforces the charter at every scope of every module the walk reaches, checks that each deviation runs only behind its gate, and reads the script the CI check loads. A deviation's function, and each function that leads to it, may be named only in the next function of its chain, which ends in the hook that checks the gate, so a module-scope call (a default, a decorator or a class body included), an alias or another caller is refused, in its own file or through any import of its module; tests drive each hook to show it checks its gate first. It refuses standard-library helpers that import a module named by a string, such as `pkgutil.resolve_name`, `pydoc.locate` and `logging.config.dictConfig`, matching each by the callable it resolves to through the file's imports, so `timeit.default_timer` or a local named `locate` is not refused. It also refuses `pytest.importorskip`, the pytest plugin-manager methods that import a plugin by name (`import_plugin`, `consider_pluginarg`, `load_setuptools_entrypoints` and the rest) and any binding of `pytest_plugins`, at any scope: by assignment, import or import alias, def or class, except or match capture, parameter or type parameter. It resolves each imported name through the directories `tests/conftest.py` puts on sys.path ahead of tests/, read from that file. It also refuses `pydoc.safeimport`, `pydoc.importfile`, `pydoc.apropos`, `pkgutil.get_data`, `unittest.main` and `unittest.TestProgram`, and a test loader's `discover`, each of which imports or runs what it is given on every call, and pydoc's `resolve`, `render_doc`, `doc`, `writedoc` and `help`, and the `package` of `doctest.testfile` and `DocFileSuite`, when the module is named by a literal string. It refuses the objects that run source text they are given, `code.InteractiveConsole`, `code.InteractiveInterpreter`, `code.interact` and `trace.Trace`, where they are made, since `push` and `run` are too common to refuse as method names; a Trace used only for `runfunc` is refused too. It refuses `runeval` by name, and `types.FunctionType` and `types.LambdaType`, since a function made from a code object compiled from source runs it when called. Each refused row asserts the violation it plants, by file, line and kind. A directory counts as a module only with an `__init__.py`, so a data directory named like an installed package (`tests/yaml/`) no longer hides that import, and one named like a standard-library module no longer reads as shadowing it; an import of a `tests/` directory without `__init__.py` is judged like any other name, and so refused.
- The charter and the pin's docstring state what the pin cannot see: a callable reached through getattr or a computed name; a helper matched by its dotted path whose module is bound other than by an import (a parameter, an assignment, a star import), or may not be under an import name reused for another module; `pytest_plugins` bound through setattr or globals(); a function type reached other than through `types`, or a code object assigned to a function's `__code__`; a directory `tests/conftest.py` puts on sys.path other than by `sys.path.insert`; string routes too common to refuse, such as mock.patch targets and pickle loads; a pydoc or doctest helper given a module or package name that is not a literal string; the help method of a `pydoc.Helper` and the run method of a `pydoc.ModuleScanner`; and an encoding named by a string, as `codecs.lookup`, `str.encode` and `bytes.decode` take one. A dynamic import callable is matched by name wherever the walked file names it, and an instance-method helper by attribute name wherever the file reaches it as an attribute. Tests pin the binding statement in both directions, and each listed blind spot has a row.

### Fast-suite test selection

- The resolver no longer reads a bare `"__init__.py"` string as a script that a test runs, which had pulled unrelated modules into the closure. A path that carries its directory still resolves.
- The resolver follows a read of an anchored directory joined to file names (`ROOT / "hooks" / "x.py"`, `joinpath`, `os.path.join`), resolving names per scope as Python does, and through parameters that a default value or an in-module call gives an anchored path. A joined name counts as its strings when every binding of it in the module is a string literal or a loop over a literal tuple or list, in place or held by a name bound once, by a plain or annotated assignment, in the module body or a class body; `os.curdir` and `os.pardir` count as `.` and `..`; an f-string with no placeholder counts as its text. A join whose name it cannot read (a parameter, a call, an f-string with a placeholder) still names no file and records nothing, and the resolver's docstring says so. A joined file that the change deletes counts too, as a deleted import does, so a test that reads it only through a join is re-selected. A pathlib constructor (`Path`, `PurePath`, and their posix and windows forms) given more than one argument with an anchored first one, and `.with_name()`, `.with_stem()` or `.with_suffix()` on an anchored path, are not followed: each records an unproven site. So does a joined name that a loop takes from a table whose binding depends on scope (a parameter of that name, or a class body that binds a name bound elsewhere too), since the module-wide reading would name the wrong file. So does an anchored argument a call passes into a def's `*args` or `**kwargs`, and an argument a call unpacks into a def of the module (`*value`, `**value`) whenever the value may hold an anchored path: a list, tuple, set or dict holding one (a dict's keys included, since `*` unpacks them), a list, set, dict or generator comprehension that yields one, a container a method such as `.append`, `.extend`, `.add`, `.update` or `.setdefault` fills with one (except a container reached through an imported name, such as `sys.path`), a call that hands a container's items on (`.copy()`, `.keys()`, `.values()`, `.items()`, `.get()`, `.pop()`, `iter`, `next`, `filter`, `zip`, `enumerate`, `itertools.chain`, `dict.fromkeys` and the `collections` containers), a name bound to one, a parameter a call fills with one, or a def's result that returns one. `map(...)` and any other call result count as holding none. A module whose reads reach the resolver's limits is treated as unproven, so every exclusion that loads it comes back on any change. This finds dependencies the import closure missed, among them two hooks that load a shared module by file path.

### Why

A test whose result depends on the order it runs in, or on state another test left behind, makes a green run mean less than it says. Shuffled diagnostic runs find order dependence that repeated runs in one order cannot, and the gate must stay deterministic while they do.

## v4.8.33: guard identity payloads, scope project reads, and cascade re-keys

### Summary

The fetch widening exists because that belt runs after the SQL limit: without it a stale hit inside the top N silently shortens the result list. Prefix scoping separates discovery from capability: a prefix is a discovery handle and must not enumerate another project's rows, while a full 32-character id is a capability the caller already holds and stays project-blind. The escaper's injectivity is what makes its markers trustworthy: if a typed `a<U+000A>b` rendered identically to an escaped newline, the escape would be unreadable exactly where it matters.

- Worktree records: a record is trusted only when the checkout it names CONTAINS the declared worktree, and the relationship is verified when the record is written -- while the declaration still exists and git can prove it, which is exactly what `git worktree prune` removes. One visible limit follows: a worktree created OUTSIDE the repository (`git worktree add ../feature`) and later pruned is no longer resolved from the record. After pruning it is indistinguishable from a record naming someone else's repository, so it falls through and is refused rather than redirecting a write into that repository. The pin cap cannot check the main checkout's document in that shape either: it allows the edit with an advisory naming the unknown root rather than passing it silently.
- Session state: a start whose session directory cannot be written now says so on the user-visible channel. The context file and the journal are reported separately, so a cold start that loses both names both; previously the only trace was hook stderr, which the platform does not show, while the project-document failure in the same run surfaced normally.
- Worktree listing: read NUL-separated so a path containing a newline survives, with an admin-gitdir fallback for a git without that option, and a raw toplevel read so paths ending in whitespace compare like with like.
- Path bytes: every git call that returns a path decodes with `surrogateescape`, so a project or worktree whose path is not valid UTF-8 classifies normally instead of failing session start. One such worktree no longer breaks the classification for every worktree of that repository.
- Staged names: a file whose name is not valid UTF-8 can no longer evade a suffix-based check. Two layers did it, and both are fixed. By default git C-quotes such a name, so the commit hook received `"x\377.env"` instead of the real bytes, it ends in a quote, and the `.env` test missed it; that mangled name was the defect under a default config. With `core.quotePath=false` the locale decode instead raised `UnicodeDecodeError` and skipped every scan. Git is now read NUL-separated and decoded with `surrogateescape`, so the real name reaches the checks either way; the same change keeps a staged binary file's content from aborting the scan.
- Commit scan: the secret scan checks every staged file in every repository, with no path exempt, and no longer blocks its own maintenance. Its detection patterns and its test fixtures are written so their source contains no contiguous match.
- Contract change: the pin-cap gate and the pin marker writer bind the managed document by IDENTITY -- the two canonical paths under the memory root -- not by containment, because PACT creates worktrees at `$REPO_ROOT/.worktrees/{branch}`, inside the root. For a linked worktree of a main checkout, in an untampered checkout, its own gitignored CLAUDE.md is therefore never the managed document, whether the worktree sits beside or inside the main checkout, with or without `CLAUDE_PROJECT_DIR` set. A worktree session writing main's file is still denied at the cap.
- Restored context names its source session neutrally and computes no liveness state, so a session killed before it recorded an end still restores.
- Journal tokens: the pin marker writer reports `noop_not_the_managed_document` for a target that is not the managed document, and `noop_memory_root_unknown` when the project memory root is unknown. The hook prints nothing; `pin_marker_write.outcome` is the only surface, and nothing in this plugin reads it.

### Why

The worktree copy was a shadow document: every resolver preferred it, memory syncs landed in a file deleted with the worktree, and the pin gates stopped recognising the real project file. An earlier change had stopped teammates doing this, and the lead case needed a decision about where that memory belongs; the answer is the main checkout. The obvious fix, skipping creation in a worktree, cannot work, because the session-resume writer creates the file on its own. Verification covers a census of the writers and readers, per-arm ablations that revert a production site, a 47-module symbol census run locally, and the full suite in CI.

- Rule B: a non-lead completing a non-exempt task with an owner gets `completion_disputed` plus a `self_completion` or `non_lead_completion` advisory, closing the peer-task and reassign-then-complete escapes.
- `is_self_complete_exempt`: a cloud actor-type surface keeps the secretary exempt where no team config exists; when the actor's name is known it must equal the owner, so `owner="secretary"` cannot be borrowed.
- Cloud roster: a lead-written append-only `teams/<team>/pact-roster.jsonl` (intent / bind / confirm per spawn) cross-checks names against `meta.json`; `dispatch_gate` records foreign spawns; local sessions read and write no roster.
- `lifecycle_decision` journal events carry the resolved actor (never `agent_id`); protocol text edited identically in `pact-completion-authority.md` and `pact-protocols.md`.
- 73 edge-case tests, three frames captured from a live cloud probe, and a live-replay regression test for the roster.

### Why

A gate that never fires is worse than none: it reads as coverage. Rule B shipped only after a live probe on real TaskUpdate frames confirmed that `agent_type` separates the lead from teammates — the lead's completion stayed silent, teammate and peer completions were flagged, and the secretary's own briefing was not. Known gaps are documented and pinned: tmux teammates are not covered, and the in-process id shape is still unmeasured.

# Changelog

All notable changes to the PACT plugin, newest first. Each version's section
is that version's GitHub release: when a version bump reaches `main`,
`.github/workflows/release.yml` tags it and publishes the section.

Format: a section starts with `## v<version>: <short summary>`, where the
summary is printable ASCII, em dash or en dash only and the text after `## `
becomes the tag message, followed by `### Summary`, `### What landed` and
`### Why`. A section ends at the next `## vX.Y.Z: ` heading. To keep the
section split identical to what GitHub renders, the file uses a restricted
Markdown: LF line endings; no HTML comments or HTML blocks; no fenced code
blocks (no run of three backticks or three tildes anywhere; inline `code` is
fine); no collapsible details or summary HTML tags; no line starting with
`<` (write links as `[text](url)`); no lines made only of `=` or `-`; and
every heading that names a version is exactly `## vX.Y.Z: <short summary>` at
column 0. Inside a section use `###` or deeper; an `## [Unreleased]` heading
goes only above the newest version. Every PR checks the whole file with
`.github/scripts/check-release-notes.sh`.

## v4.8.36: find order-dependent tests and isolate the state tests shared

### Summary

The full suite can now be run in a shuffled order on demand, and only on demand: pytest-randomly is pinned in the CI constraints and blocked by default, so the merge-queue gate, the fast suite and every local or agent run keep file order.

### What landed

- `constraints-ci.txt` pins pytest-randomly 5.1.0, and the root `pyproject.toml` blocks it by default with `addopts = "-p no:randomly"`, so every gate, fast-suite and local run stays in file order. The pytest child sessions the suite starts now pass `-p no:randomly` themselves, because a child rooted outside the repository does not read the root config; so does the full-collection guard's own collection run.
- The CI package set is now a hash-checked lock: `constraints-ci.txt` pins every distribution of the closure, pip included, with a sha256 hash per file, generated from the hand-edited `constraints-ci.in`, and every install site runs `pip install --require-hashes -r constraints-ci.txt`, so a missing pin or a changed file refuses the install. The environment check now parses the hashed lock and version-checks pip like any other pin. CI's install also passes `--only-binary=:all:`, so it refuses a source build, whose own build dependencies pip would install without hash checks. The local `.cursor/install.sh` keeps accepting source builds (pysqlite3 has no aarch64 Linux or x86_64 macOS wheel) and says so, and the lint gate's ruff-missing remedy prints the three commands that create the repository's `.venv`, install the CI lock (all its pinned packages, ruff among them) into it and activate it, as `.cursor/install.sh` does, instead of installing into whatever `python3` is first on PATH.
- The test session now refuses to start when pytest-randomly is loaded without an explicit integer `--randomly-seed`, whether it was loaded under its entry-point name or its module name (`-p pytest_randomly`). Losing the root `pyproject.toml` block, unblocking it in addopts, or shadowing it with a nearer pytest config file therefore fails the run instead of silently shuffling it. The gate reads a `--randomly-seed` written after a bare `--` because pytest applies it when no path precedes the `--`; rows pin that and the path-first shapes, where pytest itself stops before any test runs. New arms pin the block line and require every directory under `pact-plugin/` to resolve the root config.
- A child-pytest census in the test suite refuses a pytest child the suite starts without blocking pytest-randomly (`-p no:randomly`, or plugin autoload disabled), for the launch families its docstring lists and only those: pytest's own program (including `py.test`, the distro names `pytest-3`, `py.test-3` and `pytest3`, `.exe` names and a `uvx`-style `@version` spec), `coverage run`, an interpreter's `-m pytest` or `-m pytest.__main__` (python, pypy, ipython, graalpy, pyston, the Windows `py` launcher and the running interpreter), an interpreter word followed by `-m pytest` anywhere in the command, an interpreter running pytest's console script or `pytest/__main__.py`, any of these behind a listed wrapper (such as `timeout`, `nice`, `env`, `sudo`, `uv run`, `poetry run`, `uvx`, `pipx run`, `hatch run` or `conda run`), and any of these inside a shell's `-c` text. Every other launch form is outside the census, and its blind-spot list gives examples, not a complete set; a test keeps the docstring's family list and the code equal and requires a refused row for every family. The census reads every interpreter-named word in a launch for `-m pytest`, not only the first, so a wrapper option's value named like an interpreter (`uv run -p python3 python -m pytest`) no longer hides the interpreter after it, and an interpreter running pytest's script is found after an option the wrapper tables do not know when that option's value is itself interpreter-named, never past a known flag or a non-interpreter word (so `uv run -v echo python /venv/bin/pytest` is not refused); its wrapper option tables are read from each tool's `--help`, bash's `help exec` for the `exec` builtin, sudo's manual page, micromamba's source, and the current documentation of `conda run`, `rye run` and `pixi run`. The launch aborts before the child starts, and under xdist a worker hands its refusals to the controller, so a test that swallows the error still fails the run. A child that loads pytest-randomly is refused, and the last randomly flag wins across the whole argv, including a `-p` after a bare `--`, which pytest also reads. A child blocked through `PYTEST_ADDOPTS`, an `env` assignment or a disabled autoload is accepted, with `env -i`, `env -u` and `sudo` applied to the environment it checks, and so are `pdm run --env` and micromamba's `-e`/`--env`; `--clean-env` (micromamba, pixi) empties that environment, so a launch that drops the parent's block is refused. Every wrapper-table entry has a row that fails when the entry is deleted, and 25 entries no input could reach were removed. An interpreter is recognised by its exact name (a test pins that `python-config` or `pythonista` is not one) in the program position, so `git grep pytest`, `pip install pytest` and `pip install python-dateutil pytest` are not refused. A census fault, a launch the census cannot read, fails the run only when the launch names pytest, and its line names the test that made it; a malformed launch of another program is left to that program's own error.
- The clock-shift census now works under xdist: each worker hands its misses and child count to the controller, which fails the run and judges "children loaded the shim" once for the whole run, ignoring the workers' own ledger lines, which had made that check pass inside any worker. A crashed or restarted worker's pid is excluded too, taken from the subprocess its execnet gateway holds, so a crashed worker's own ledger line no longer counts as a child's. A test pins that a change to the census still re-selects its instrument tests in the fast suite.
- The full-run record now carries the exit status the process returns: its session-end hook runs last and reads the session's status, so a run that a census or the environment binding failed is recorded as failed. Both censuses now raise only a clean status to 1, so an interrupted, internal-error or usage-error run keeps its own status.
- The full-suite workflow takes an optional `shuffle_seed` dispatch input. A guard step admits only an empty value or a decimal seed of up to 9 digits with no leading zeros, refusing anything else before setup. A seeded dispatch runs the suite in pytest-randomly's shuffled order, and the evidence artifact name ends in `ordered` or `seed-N`. Merge-queue and push runs pass no seed, so their pytest argv is unchanged. A seeded run also passes `--randomly-dont-reset-seed`, so pytest-randomly does not reseed the random generators before each test; the seed still sets them once at session start. The guard spells out its digit classes and is pinned by executing it against accepted and refused values. That arm gives its child processes a sandbox HOME. On Linux it also runs every row under a locale it builds, where bash's `[0-9]` matches non-ASCII digits, so reverting the guard's spelled-out digit classes fails it, and a missing `localedef` fails loudly; on other platforms only the ASCII rows and a static no-range check run.
- `scripts/compare_full_suite_results.py` accepts the seeded run line and records each run's pytest-randomly seed from its own header line, beside the run identity and outside the environment, so a shuffled run compared with an ordered one reports a real test difference as a delta, never as unattributable evidence. A log with two seed lines is refused, and so is a log that carries a seed line beside the older unseeded run line, which cannot load the plugin; an ordered run on the current run line still reads as having no seed. The seed is read only from the full-suite step's own report header, so a seed line a test prints in its captured output is ignored, and a log with no session banner after the run command is refused instead of being read as an ordered run. A seed that is not 1 to 10 ASCII digits is refused as evidence instead of crashing the comparator or being accepted. The comparator accepts the seeded run line only with `--randomly-dont-reset-seed` inside the seed expansion; the earlier seeded form is refused. It also reads a census failure from the full-suite step's session-finish output, and reports a green run that a census failed as a census outcome with a named census delta, instead of refusing it as broken infrastructure. A census-shaped line in a test's captured output is ignored, and a red run still records any census that failed it. A green run whose log carries a census failure beside exit status 0, or beside an exit status a census cannot produce, is refused with a message naming the census and the exit status. The comparator's outputs move to schema_version 2: `comparison.json` and, newly, every `runs.jsonl` record.
- The test suite runs hypothesis with no example database, and keeps hypothesis's storage in the session's sandbox HOME instead of `.hypothesis/` in the tree, so no run replays or reads what an earlier run left behind.
- The merge guard's cached git alias and git command lookups are cleared around every test, so the first test in a worker no longer fixes the answer for the tests after it. Its arm fills both caches before the test and checks them after it, so it fails when either clear is missing under any order or xdist distribution.
- The test suite sets `GIT_CONFIG_NOSYSTEM=1` in its own environment, so the suite process, every child that inherits that environment, and every child built by the shared `child_env` fixture ignore the machine's system git config. A child environment a test builds from scratch without the variable still reads it.
- Teammates and the cold reviewer record the HEAD and the worktree status immediately before and after each test run they report. If either changed during the run, the result is re-run or reported as unattributable, not as a pass or a failure of the change.
- The embedding catch-up test loader no longer evicts the real `scripts.embeddings` and `scripts.embedding_catchup` modules, so a test that runs after it on the same worker patches the same module object the code under test uses.
- The two gate-reload test modules restore the inline-mission and dispatch-variety mode variables to their prior values at teardown instead of deleting them, so an exported mode no longer vanishes for every later test on the worker. The teardown pin also catches an environ write made through an alias such as `from os import environ`.
- The mint-matrix corpus and the Cat-2 name count read only git-tracked files, so an untracked file in a working tree (a probe another worker planted, a local draft) can no longer add rows or mask a dropped name. A reviewed reach entry in `scripts/fast_suite_exclusions.json` keeps the fast suite re-selecting the mint matrix when a test module changes.
- The fast-suite resolver no longer reads a bare `"__init__.py"` string as a script that a test runs by path. Joined onto a directory, that string names the directory's own package marker, but it resolved against every import root and pulled about 45 unrelated modules into the closure. A path that carries its directory still resolves, and no fast-suite selection for a single changed path changes (measured over every tracked path).
- Tests whose memory saves reach the session embedding marker now use a fresh session id per test and remove that marker afterwards, so no test leaves a fixed-id `/tmp` marker that makes later runs and other workers skip the embedding catch-up. The session-init export test now fails if it leaves its embedding marker in `/tmp`. The session id other test modules import is now unique to each process, and the suite fails any test that leaves an embedding marker under it. An arm runs a rig test under the real conftest that leaves such a marker and expects the failure, and another proves a repeated per-test session id is refused.
- The idle-preamble test rig now requires a tmp path, so it can never fall back to patching HOME to the shared `/tmp`.
- A runtime HOME census in the test suite, beside the child-pytest and clock-shift censuses, replaces the static home-isolation scan; the four runtime sandbox-HOME checks that shared the scan's file (a child resolves its home and config root outside the real home, the session and collection run in the sandbox, and the embedding cache stays out of the sandbox HOME) now live in their own module, which keeps the scan's always-run slot in the fast lane. Through the `subprocess.Popen` and `os.posix_spawn` audit events (`subprocess.run`, `call`, `check_call`, `check_output` and `Popen`, `os.popen`, asyncio's `create_subprocess_exec` and `create_subprocess_shell`, and `os.posix_spawn` and `posix_spawnp`) it refuses a child whose environment is given without a HOME key, and an inherited one while the suite's own environment has no HOME, as after `monkeypatch.delenv("HOME")`: a child without HOME finds its home through the password database, which is the real one. A refusal aborts the launch before the child starts and names the test; under xdist a worker hands its refusals to the controller, and the census raises only a clean exit status to 1, so the full-run record and the comparator, which now names the `home` census, see it like the others. A clean run ends with one information line, `HOME CENSUS: installed, N launches checked, 0 refused` (`1 launch checked` when N is 1), which the comparator does not read as a census failure. The only exemption is `@pytest.mark.child_env_without_home(reason=...)` with a non-empty reason. Its docstring names what it does not see, such as `os.spawn*`, `os.exec*`, `os.system`, multiprocessing's start methods and launches through ctypes. It judges an inherited launch by `os.environ`, not by the C-level process environment, so a change made with `os.putenv` or `os.unsetenv`, or a replaced `os.environ`, is not seen as such, and its opt-out marker exempts a marked test anywhere in a session that loads `pact-plugin/tests/conftest.py`, one under `pact-plugin/skills/` included, while a session that does not load that conftest, such as a run of `pact-plugin/skills/` tests alone, has no census and prints no census line. Run over the 319 test modules that launch a child, it refused nothing. Two claim-gate tests that started their hook without HOME now pass the sandbox HOME, and two cache-binding helpers carry HOME from their caller explicitly. The install-line copies in the environment check's remedy, the install tripwire and the lock input's header are now pinned to the local and CI lines.

### Why

A test whose result depends on the order it runs in, or on state another test left behind, makes a green run mean less than it says. Shuffled diagnostic runs find order dependence that repeated runs in one order cannot, and the gate must stay deterministic while they do.

## v4.8.34: capture comparable full-suite diagnostic outcomes

### Summary

The full-suite workflow's manual dispatch can now select whole-file or per-test xdist scheduling while keeping whole-file scheduling as the default everywhere else. Manual runs also emit JUnit XML and upload it with the existing collection and run records, so diagnostic comparisons can detect per-test outcome changes without replacing the schema-v3 merge-gate evidence.

### What landed

- `.github/workflows/tests.yml` adds a constrained `dist` dispatch choice: `loadfile` by default, with `load` as the only alternative. The dispatch value reaches pytest through the job-level `DIST` environment key and is never interpolated into the shell command, so a value outside the two options cannot execute as shell (and an invalid one fails loudly at argparse). A guard step case-checks `$DIST` against the two enum values before any setup work, refusing by name without echoing the value, so an out-of-enum API dispatch fails in seconds rather than at argparse after the model warm. The single unrestricted pytest invocation has no path operands and resolves to the existing default command outside explicit diagnostic dispatches. The required `full-suite` job remains scalar, and the existing full-collection, full-run, and before/after environment verifiers keep their ordering.
- The pytest step writes `.full-suite-results.xml`. A red-or-cancelled-step upload preserves that JUnit file, `.full-run-record.json`, and `.full-collection-record.json` under a unique run/attempt artifact name that carries the dispatch `dist` resolved to one of its two enum values, so the name sink is as constrained as the shell sink; every dispatch uploads and a green merge-group or push run uploads nothing. The upload is the job's final step, after the post-run environment check, so a failure in that check still uploads the evidence it invalidated, while the environment check remains the last command the job runs. A hard timeout bounds what this step can preserve: pytest writes the JUnit file and the run record at session finish, so a killed run leaves only the collection record written before the tests, and whether GitHub executes an `always()` step after a `timeout-minutes` kill is GitHub's behaviour rather than something this workflow can demonstrate. Missing evidence is an error, and `include-hidden-files: true` is mandatory for these dotfiles; the upload comment names the deliberate empty-evidence cancellation, where a run cancelled before the collection step reddens the upload because no files exist — the loud no-evidence signal rather than an upload defect. The upload action is pinned to `actions/upload-artifact` v7.0.2 by full commit SHA, and the JUnit dotfile joined the other one-run records in `.gitignore`.
- CI contract tests pin the input, the job-level `DIST` key and the expression it derives from, the exact dynamic command, artifact shape, name and placement, the per-workflow action allowlist and pin, and final environment check. One strict `shlex` normalizer accepts only the reviewed dynamic command and resolves it to the static default for local collection parity; expression fragments, extra arguments, missing JUnit output, and selection flags fail instead of reaching local pytest. Mutation arms cover altered commands, hidden-file omission, missing paths, wrong upload conditions or placement, and unpinned actions.
- `scripts/compare_full_suite_results.py` and its focused tests compare per-test JUnit outcomes without replacing schema-v3 certification. The comparator preserves duplicate cases, reconciles raw XPASS evidence and skip identities, and fails closed on missing or ambiguous evidence; it also normalizes the real Actions log envelope, quoted distribution arguments, summary timing skew, and invocation-relative skip paths. Before/after environment steps must exist and conclude success, and the overall run conclusion must agree with the test outcome, so failed infrastructure cannot be certified as clean. Environment differences refuse a comparison only on material axes (platform, interpreter, pins, job names); ephemeral runner instance ids and incidental log lines never suppress a delta. A run that reports a collection error is deliberately refused as invalid evidence rather than compared, because a corpus that did not collect cannot support an unrestricted comparison. The encoding refusal is total over every document the parser accepts: a NUL byte is refused before parsing, which closes the BOM-less wide encodings that defeat a byte scan while expat still auto-detects them, and XML 1.0 forbids U+0000 outright so no well-formed document is refused. A document above a named size bound is refused as invalid evidence, and the element pytest writes for a strict xfail that passes is classified with the run's own accounting instead of being refused as an unknown form. Every downloaded artifact is read through one bounded helper — the JSON records and metadata at 8 MiB, the run log at 32 MiB, the JUnit artifact at 8 MiB, halved from 16 to bound the parse amplification a hostile nested document can spend before refusal — with refusals naming the file and the bound, and RecursionError is mapped to refusal like any other parse failure; the size guard's encoding totality is bounded by the parser's own encoding set rather than the byte scan, which is what stops EBCDIC-family bytes that pass the scan. The run-layout epilog and module docstring name the four identity keys a metadata.json must carry at top level — attempt, databaseId, workflowDatabaseId, headSha, normalized beside the API response's own spellings, with an un-normalized object refused — and a real-child arm pins the xfail teardown shape: an expected failure absorbs its broken teardown into skipped children on one JUnit element, so a future pytest that emits the error shape reddens the arm instead of drifting the aggregates.
- `pact-plugin/tests/test_memory_store_isolation.py` removes the predecessor sentinel that made memory-init reset verification depend on test order and worker placement. Both tests now establish their own initialized state, and the reset test calls the owner reset before its unchanged clean-state assertion; a worker-local collection-dirty observer proves removal of the real autouse reset under serial, load, and loadfile without an ordering assumption, while standalone, reversed-order, xdist-load, and reset-removal controls cover the isolation.
- `pact-plugin/tests/test_merge_guard_perf.py` pairs target and reference timing observations so normalized cost no longer depends on separately timed blocks, and uses median raw target times to reject size-specific fast outliers without hiding sustained quadratic scaling. Best-of-K normalized cost, the 3.0 raw ratio bound, the 4000.0 ceiling, and unbounded-prefix detection remain, with fake-clock and mutation controls proving the schedules still detect regressions.
- `scripts/verify-gate-tree.sh` now brackets local pytest with before/after HEAD and complete porcelain comparisons. Stable, moved, and red-child runs are distinguished explicitly, green moved trees become unattributable, and capture paths inside the declared tree are refused before any snapshot or test work. The containment check fails closed when the interpreter that resolves the capture path fails or prints nothing, so a broken `python3` refuses rather than letting the capture land inside the measured tree. A tree with no commit at HEAD is refused before pytest starts instead of stamping an empty head after a full run, and a green-but-unattributable run now exits 6 — distinct from the usage/red-pytest exit 1 and above pytest's own 0-5 range, so a wrapper exit names its cause without reading the capture. The canary pass condition and refusal list were updated to match, while decisive certification still uses a detached clean worktree. The symlink-refusal arm asserts the containment message by name, so an exit-2 refusal for any other reason cannot read as that arm's pass.
- Instruction-surface tests for corpus writers, markers, lazy-load cross-references, and peer injection now enumerate their intended tracked files rather than stray untracked matches. Local controls check root/pattern filtering, known members, deletion detection, empty-population refusal, and the original raw-glob failure mode.
- Harvest, import-bar, non-TTY, manifest, prose-root, and Python-floor tests now enumerate their shipped populations from git while retaining synthetic and intentional disk-based discovery. Known-member, untracked-exclusion, deletion, and count controls prove the new oracles are non-vacuous. Probe writers use isolated synthetic repositories rather than mutating the shared checkout, so raw-glob consumers cannot collide with them. The import-bar synthetic model also copies only its two tracked Python sources, closing the fixture-copy path around tracked enumeration without weakening deletion checks.
- Post-merge, session-context, store-access, run-scope, and wake-ordering tests now use checked Git-index pathspecs for shipped artifacts while preserving deleted-member failures and synthetic temporary-root walks. Before/after probes and real deletion controls verify the isolation, and a converted population is bound by an arm that reverts its own consumer rather than the shared helper: reverting a conversion to its previous filesystem walk reddens the arm, naming the untracked member that joined. Where a population is read as text its enumeration no longer requests deleted index entries, so a locally deleted tracked file produces one named missing-population failure instead of a read error; the one exception is a fixture's declared known-member anchor, whose absence is asserted by name because its presence is what proves the population non-empty.
- Agent, command, and skill structure tests now enumerate shipped files from the Git index with nonempty, rooted, and known-member controls. Filesystem walking remains only for gitless exports, while deleted tracked entries stay visible and raw-walk mutation controls preserve the original failure signal. A shared direct-import helper makes corrupt-index, unsafe-repository, transient, and every other nonzero `ls-files` result fail closed instead of widening to untracked files. The shared enumerator normalises its root to an absolute path before it looks for a checkout marker, refuses a scan start point or an enumerated file that resolves outside the root while still enumerating an in-root symlink, and uses the filesystem fallback only when the enclosing repository tracks nothing under the root, so a checkout-free copy nested inside an unrelated repository works instead of refusing. The shared fixture's accepted-boundary note names the partial-overlap case — an enclosing repository that tracks a strict subset under the copy yields that subset as the population — the unused pathspec parameter is gone, and an `ls-files` failure names the exact prefixed pathspec git received rather than the caller's unprefixed spelling. The installed-layout skip now classifies by failure shape: only an empty tracked population is a layout omission that skips with a named reason, while the helper's fail-closed refusals fail in every layout instead of skipping as though the population were absent — the assertion catch narrows to the empty-population message and re-raises everything else. Census depth is now deliberate per directory rather than incidental: the agents and commands censuses enumerate flat, matching the agent-definition census, while the skills and protocols censuses recurse because their corpus genuinely nests below the top level. Every refusal exit of the tracked-files helper — a `.git` marker over a broken repository, and a failing index query in a healthy repository — now carries an arm asserting its own refusal message, so a fall-through to filesystem enumeration fails by name.
- Verification closed the census's 45 of 45 confirmed run-dependent walk hits across 18 modules, with required tracked-deletion controls preserved. A re-probe of the 74 rows the census had set aside then tested each against a needle built for its enclosing assertion rather than the census's generic fixture: most set-aside rows proved live, so the probe standard is now content that reaches the enclosing assertion, not merely a changed working-tree state. The live walks were converted in this PR through tracked enumeration. The final census ledger records 48 rows fixed and verified, 537 evidenced non-dependent, and none left unknown — the two formerly-unknown rows were re-probed from supplied evidence, decided live, and converted with mutation arms. The census scanner derives its roots from a loop over literal directory names and was accepted only after the per-exclusion root map measured byte-identical before and after across all 24 exclusions. A review round also found and fixed two blocking defects in this surface, because the comparator refused the unexpanded `DIST` token the runner echoes into the log and the fast-lane reach rule stopped recognising a converted module's tracked scan call. The scanner also no longer keys functions by bare name — same-named definitions are unioned, so a module stays selected when a shadowed redefinition reaches a scan — and its per-module wrapper set is computed once instead of twice.

### Why

Repeated diagnostic runs need per-test evidence, not only aggregate counts: equal totals can hide two tests swapping pass and skip. JUnit adds that comparison surface beside the existing certification records, while the constrained dispatch interface exposes per-test scheduling without arbitrary pytest arguments or a new job matrix. The tracked-population, memory, timing, and tree-attribution fixes remove local run conditions that could change test outcomes or make a green run unattributable, so repeated runs measure the same shipped suite.

## v4.8.33: guard identity payloads, scope project reads, and cascade re-keys

### Summary

Every identifier the memory layer binds is held to one rule: a non-empty string free of C0, DEL and C1 control characters and of lone surrogates. A SUPPLIED `project_id` or `session_id` is validated where it enters — in the constructor when it is a constructor argument, and in the payload guard on `save` and `update`. A DETECTED value is NOT validated at construction: it is adopted as found, because a by-id `get`, `update` or `delete` never binds it and must keep working. Every path that would bind the value guards where it binds — project-scoped reads treat an unusable detected `project_id` as an unresolvable identity and answer empty or zeroed, a prefix is refused exactly as under no identity, and a `save` that would bind the value refuses at the write ingress with `ValueError` and remedy text naming the detected source — so nothing dies at a utf-8 TEXT binding. On `update` the guard is keyed on presence, never on `.get()`: `update_memory` scalar-replaces the field, so an explicit null or empty string is the de-key hazard and is refused, while an update omitting both fields leaves the row unchanged; on `save`, null still means auto-detect. A valid non-empty `project_id` re-keys the row and cascades: the memory's file links are re-pointed to the `(path, new project)` file row (created on demand) and its vector is re-stored under the new partition. The cascade runs on a change this call made OR on an invariant the store still breaks, so re-issuing an interrupted update finishes the repair instead of reading as a no-op; a faulted re-store now LEAVES the rollback-restored old-partition row in place, because every vector read confirms the stored project, the catch-up is partition-aware, and a stranded row keeps the re-issue a repair rather than letting the cascade delete a row another session had just stored. Every project-scoped read confirms a row's own stored project at the last place an id becomes a returned memory — vector hits, graph-boosted hits, file-link hits, graph context and file relations — and the vector and graph legs widen their fetches, up to bounded caps, so a discarded stale hit does not cost the caller a result slot. Prefix resolution is project-scoped across all three of its queries: a prefix that matches only another project's row resolves as no row, an `AMBIGUOUS_PREFIX` list carries no other project's rows or context snippets, and an unresolved identity refuses a prefix instead of enumerating every project's rows. A full 32-character ID remains a by-id capability, so `get`, `update` and `delete` accept an ID stored under any project, while `list`, `search` and `search_by_file` stay project-scoped. `track_file` tolerates a create race, the embedding catch-up matches the vector partition as well as the id and drops a cross-partition row before rewriting it, the `/tmp` embedding-attempt marker slug is sanitised and length-bounded, and the CLI's error-envelope escaper is total and injective.

### What landed

- `skills/pact-memory/scripts/memory_api.py`: `PACTMemory.update()` carries a payload-validation block keyed on presence (`"field" in updates`, never `.get()`, which cannot distinguish an explicit JSON null from omission), covers `project_id` and `session_id`, rejects unusable values with `ValueError` and remedy text, and runs before `_ensure_ready()` and before the memory id is resolved, so an invalid payload reports itself rather than a prefix. A non-dict payload is refused through the same channel instead of reaching a bare `TypeError`. `save()` holds a supplied `session_id` to the same rule as `project_id`, and the constructor validates both SUPPLIED identifiers. A DETECTED value — the project id from the environment, the session record, a git root or the working directory, or the session id from the session context file — is adopted as found and is NOT validated at construction, because a full 32-character by-id `get`/`update`/`delete` must keep working without binding it. The orchestrator's wait-in-silence rule now separates narration from a milestone. It stays silent on "waiting on X" and "still running". It reports a milestone, meaning something the user would act on and cannot otherwise see: a dispatch's result, a measured number, or a state change. The report is one line that carries the concrete fact rather than a description of the activity. The orchestrator relays each milestone as it reaches it, without being asked, and never polls or nudges a teammate to get one. When it wants a long dispatch reported mid-run, it asks for progress signals in that dispatch's brief, so the user sees milestones as they land rather than asking for status.

### What landed

- `agents/pact-orchestrator.md` §Wait in Silence: the list that defines a turn with no actionable content now includes "no milestone the user is owed", so that sentence is complete on its own.
- The same section gains one paragraph, placed immediately after that rule. It does the following:
  - It defines a milestone as something the user would act on and cannot otherwise see. That qualifier governs all three kinds: a dispatch's result, a measured number, and a state change.
  - It requires the relay to be one line addressed to the user. The line carries the concrete fact, and is sent only when the fact is new since the last report to the user and is not a running tally of the same work.
  - It states the tally test for a fan-out: a count of members finished is a tally, and a member's result the user would act on is a milestone.
  - It states that "No actionable content" means nothing the team needs AND nothing the user is owed.
  - It makes the orchestrator relay each milestone as it reaches it, never poll or nudge a teammate to obtain one, and ask for progress signals in the brief of a dispatch it wants reported mid-run.
  - It bounds that ban: a nudge that resolves an ambiguous teammate state under §12 Intentional Waiting is not polling for a milestone, and a milestone carried by its reply is relayed like any other.
- The paragraph separates narration from a milestone rather than carving an exception out of the silence rule. Filler calls stay with the filler-call rule, not the narration list. The surrounding anti-narration, filler-call and watcher rules keep their full force: none of their pinned phrases changed, and the section was not restructured.

### Why

The silence rule named only what is actionable for the team, so its safe reading was silence on everything. Between dispatch and the awaited event the only interim progress signal arrived in teammate notifications the user never sees. The watcher rules already require the completion report; nothing required an interim one, so the user had to ask for status repeatedly. Naming the milestone case changes what the orchestrator does on a teammate turn, without reopening the narrate-the-wait and filler-call failures the section exists to prevent.

## v4.8.19: a worktree lead writes project memory to the main checkout (issue #1653)

### Summary

A lead session started inside a linked git worktree now writes its project CLAUDE.md in the main checkout instead of planting one in the worktree. One rule decides where project memory lives: the writers, the memory sync and every advisory reader resolve the main checkout for a worktree session, and a plain session is byte-identical to before. When git cannot answer, no writer writes at all, and each reports the skip on its own channel.

### What landed

- One resolver: `session_memory_root` returns the main checkout for a linked worktree and the directory itself otherwise. It verifies the candidate as a checkout root and requires git to list the worktree, so a forged gitfile cannot redirect a write into another repository.
- One document: every session tool (the SessionStart writers, the bootstrap hooks, the pin gates, the memory sync, `archive_pin` and the advisory readers) resolves the session's project memory file through one function, so no two of them can name different files. The lead's SessionStart context names that file on a `Project memory file:` line, the memory CLI prints it with `project-file`, and the commands that edit project memory point at that line.
- Subdirectory sessions: a lead started in a subdirectory of a checkout still manages the subdirectory's own CLAUDE.md when it has one. When it has none and the checkout root has one, the lead now manages the root's file instead of creating `<subdirectory>/.claude/CLAUDE.md`.
- User-global file: a session never treats a user-global CLAUDE.md as its project memory. Two files count: the active config root's CLAUDE.md, and `~/.claude/CLAUDE.md` of the default profile. That covers a session started in either directory, a session whose removed worktree's record points at a home-directory checkout, and a subdirectory of a home-directory checkout. Files are compared by identity (a hardlink, a symlink or a case variant on a case-insensitive volume counts as the same file, and a file not created yet is matched by where it would be created), and a comparison that cannot be decided counts as the global file. The config root is made absolute against the working directory before comparing, and a relative value is also read against the project directory, so a relative `CLAUDE_CONFIG_DIR` or a `..` spelling names the same file. The session tools skip with the cause `user_global` and write nothing; when the home directory cannot be found, every root is refused with the cause `home_unknown`.
- Writers: `session_init` steps 3, 3b, 4 and 5b, the two bootstrap hooks, `realign_team`, `pin_marker_writer`, `archive_pin` and the memory sync writers all target the memory root, and each writer's targets and guards derive from that same root.
- `archive_pin` now refuses where it used to resolve: an unknown project memory root THAT EXISTS (git could not run, or a forged or unverifiable checkout), and a resolution that lands on a linked worktree copy, both raise its refusal type with a message. An archive that used to succeed against a document nothing writes now fails and says why.
- Readers: the display resolver and every advisory reader (pin-slot status, refusal reporting, stale-block directive, `track_files`, `check_pin_caps`, `claude_md_drift`, `match_project_claude_md`) resolve the same root, so no reader watches a file that nothing writes. On an unknown root the advisory readers stay silent rather than describe the worktree copy, and the pin-cap gate allows an edit with an advisory instead of passing it in silence.
- Drift cache: its format is version 3 and stores the session root and its enclosing checkout; an older entry is discarded and rebuilt on first read, so an upgrading session stops watching a stale worktree copy.
- Unknown roots: a git that cannot answer is distinguished from a git that answers not-a-worktree, and a declared directory that does not exist is could-not-run rather than a known root. A git that runs but refuses on a directory holding git metadata (a moved main checkout, a deleted worktree admin directory, or a checkout git refuses for dubious ownership) is now unknown too, so those sessions skip with the cause: a worktree no longer gets a copy of its own, and a main checkout git does not trust keeps its project memory unmaintained until git trusts it; a directory git deliberately does not search past (`GIT_CEILING_DIRECTORIES`, a filesystem boundary) is still its own project. Every writer refuses on the unknown case and reports it, rather than planting in a worktree during a git failure, and no session re-creates a declared directory to plant `.claude/CLAUDE.md` inside it.
- Symlink loops: a symlink loop in the recorded session directory or in the declared project directory is treated as an unusable path on Python 3.12 rather than raising out of session start.
- Removed declarations: the memory sync and `archive_pin` distinguish a declared directory that no longer exists from one git cannot identify. When the declared directory no longer exists and no session record recovers the main checkout, both now skip and name that cause instead of falling back to the working directory's checkout. A resolution that still lands on a sibling worktree's own copy keeps the existing refusal, and an existing base git cannot identify keeps the unknown-root refusal.
- Removed worktrees: a session whose declared worktree was deleted also keeps its session record, and that record now resolves the main checkout for the memory sync, `archive_pin` and the pin-cap gate -- verified, once the worktree is gone, against the candidate main checkout rather than the worktree listing, because `git worktree prune` deletes both on the normal cleanup path. A record that names the declaration but does not verify is not followed, and a refusal on this shape says the declared directory no longer exists rather than describing a git failure.
- Skip messages: every channel that reports an unknown project-memory root -- the SessionStart skip, the bootstrap prompt gate and marker writer, `realign_team`, the memory-sync warning and `archive_pin`'s refusal -- names the cause that occurred, and a missing directory is named by its path. Three causes are distinguished: a directory that no longer exists, an existing directory git could not identify, and an existing directory whose git answer failed verification (a forged gitfile, or a separate-git-dir worktree with no identifiable main checkout). A bare repository's worktree stays a known root, so it prints no skip line and no unknown-root text.
- Worktree saves: an archive that refused for EVERY worktree session now succeeds. The memory save compared the main checkout a worktree session retargets to against the session record's worktree path textually and refused, on live worktrees as well as removed ones; a verified worktree record now proves the two are one project, while a symlinked spelling of the same directory still refuses. The refusal's remedy no longer tells a user to re-export a directory that has been deleted.
- Worktree records: a record is trusted only when the checkout it names CONTAINS the declared worktree, and the relationship is verified when the record is written -- while the declaration still exists and git can prove it, which is exactly what `git worktree prune` removes. One visible limit follows: a worktree created OUTSIDE the repository (`git worktree add ../feature`) and later pruned is no longer resolved from the record. After pruning it is indistinguishable from a record naming someone else's repository, so it falls through and is refused rather than redirecting a write into that repository. The pin cap cannot check the main checkout's document in that shape either: it allows the edit with an advisory naming the unknown root rather than passing it silently.
- Session state: a start whose session directory cannot be written now says so on the user-visible channel. The context file and the journal are reported separately, so a cold start that loses both names both; previously the only trace was hook stderr, which the platform does not show, while the project-document failure in the same run surfaced normally.
- Worktree listing: read NUL-separated so a path containing a newline survives, with an admin-gitdir fallback for a git without that option, and a raw toplevel read so paths ending in whitespace compare like with like.
- Path bytes: every git call that returns a path decodes with `surrogateescape`, so a project or worktree whose path is not valid UTF-8 classifies normally instead of failing session start. One such worktree no longer breaks the classification for every worktree of that repository.
- Staged names: a file whose name is not valid UTF-8 can no longer evade a suffix-based check. Two layers did it, and both are fixed. By default git C-quotes such a name, so the commit hook received `"x\377.env"` instead of the real bytes, it ends in a quote, and the `.env` test missed it; that mangled name was the defect under a default config. With `core.quotePath=false` the locale decode instead raised `UnicodeDecodeError` and skipped every scan. Git is now read NUL-separated and decoded with `surrogateescape`, so the real name reaches the checks either way; the same change keeps a staged binary file's content from aborting the scan.
- Commit scan: the secret scan checks every staged file in every repository, with no path exempt, and no longer blocks its own maintenance. Its detection patterns and its test fixtures are written so their source contains no contiguous match.
- Contract change: the pin-cap gate and the pin marker writer bind the managed document by IDENTITY -- the two canonical paths under the memory root -- not by containment, because PACT creates worktrees at `$REPO_ROOT/.worktrees/{branch}`, inside the root. For a linked worktree of a main checkout, in an untampered checkout, its own gitignored CLAUDE.md is therefore never the managed document, whether the worktree sits beside or inside the main checkout, with or without `CLAUDE_PROJECT_DIR` set. A worktree session writing main's file is still denied at the cap.
- Restored context names its source session neutrally and computes no liveness state, so a session killed before it recorded an end still restores.
- Journal tokens: the pin marker writer reports `noop_not_the_managed_document` for a target that is not the managed document, and `noop_memory_root_unknown` when the project memory root is unknown. The hook prints nothing; `pin_marker_write.outcome` is the only surface, and nothing in this plugin reads it.

### Why

The worktree copy was a shadow document: every resolver preferred it, memory syncs landed in a file deleted with the worktree, and the pin gates stopped recognising the real project file. An earlier change had stopped teammates doing this, and the lead case needed a decision about where that memory belongs; the answer is the main checkout. The obvious fix, skipping creation in a worktree, cannot work, because the session-resume writer creates the file on its own. Verification covers a census of the writers and readers, per-arm ablations that revert a production site, a 47-module symbol census run locally, and the full suite in CI.
